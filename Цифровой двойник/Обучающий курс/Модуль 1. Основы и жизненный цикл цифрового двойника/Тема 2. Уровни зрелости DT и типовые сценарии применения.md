# Модуль 1. Тема 2. Уровни зрелости DT и типовые сценарии применения

> Модуль 1 «Основы и жизненный цикл цифрового двойника» · Тема 2 из 5

## Учебные цели

После изучения темы студент сможет:

- перечислить шесть уровней зрелости цифрового двойника и назвать признак, отличающий каждый уровень от предыдущего;
- определить фактический уровень зрелости конкретного внедрения по данным, моделям и типу принимаемых решений;
- сформулировать критерии перехода на следующий уровень и оценить, выполнены ли они;
- подобрать типовой сценарий применения под отрасль и задачу заказчика;
- провести анкетирование сценария и получить численную оценку его готовности.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Уровень зрелости DT | Характеристика глубины функциональности двойника: от описания состояния до автономного управления |
| Описательный уровень | Двойник хранит структуру и характеристики объекта, но не отражает текущее состояние |
| Информационный (мониторинговый) уровень | Двойник показывает актуальное состояние объекта по данным телеметрии и реестров |
| Диагностический уровень | Двойник объясняет причины отклонений: локализация неисправности, корневой анализ |
| Предиктивный уровень | Двойник прогнозирует будущее состояние: отказ, дефицит, перегрузку, срок исчерпания ресурса |
| Предписывающий уровень | Двойник предлагает конкретное действие и оценивает последствия альтернатив |
| Автономный уровень | Двойник реализует решение без участия человека в пределах заданного коридора допустимых воздействий |
| Критерий перехода | Проверяемое условие, без выполнения которого следующий уровень недостижим или недостоверен |
| Коридор автономии | Границы параметров и ситуаций, в которых двойнику разрешено действовать самостоятельно |

## 1. Шесть уровней зрелости

Шкала зрелости отвечает на вопрос «на какой вопрос умеет отвечать двойник». Уровни накопительны: каждый следующий требует работоспособности всех предыдущих.

```
  1. Описательный    "Что это за объект и как он устроен?"
        │
  2. Информационный  "Что с ним происходит прямо сейчас?"
        │
  3. Диагностический "Почему это происходит?"
        │
  4. Предиктивный    "Что произойдёт дальше?"
        │
  5. Предписывающий  "Что нужно сделать и что будет в каждом варианте?"
        │
  6. Автономный      "Сделай сам в пределах разрешённого коридора"
```

### Признаки уровней

| Уровень | Признак, что уровень достигнут | Признак, что уровень только заявлен |
|---------|-------------------------------|-------------------------------------|
| Описательный | Есть полная структура объекта, справочники, идентификаторы, паспорт данных | Структура есть, но объекты дублируются и не сопоставляются между системами |
| Информационный | Состояние обновляется автоматически, известна задержка и полнота данных | Данные обновляются вручную или задержка неизвестна |
| Диагностический | Отклонения не просто фиксируются, а сопоставляются с причиной по модели | Есть цветовая индикация «красный/зелёный» без объяснения причины |
| Предиктивный | Прогноз проверяется постфактум, известна его точность на исторических данных | Прогноз выдаётся, но никто не измеряет, сбывается ли он |
| Предписывающий | Рекомендация содержит альтернативы, ограничения и оценку последствий | Выдаётся одно «оптимальное» действие без допущений и ограничений |
| Автономный | Заданы коридор автономии, условия отката и журнал воздействий | Автоматика работает, но границы вмешательства не описаны |

## 2. Уровень — данные — модели — эффект — риски

| Уровень | Требуемые данные | Класс моделей | Основной эффект | Ключевые риски |
|---------|------------------|---------------|-----------------|----------------|
| Описательный | Паспорта, структура, справочники, геометрия | Структурные, справочные | Устранение разночтений, единый язык объектов | Устаревание, дубликаты объектов |
| Информационный | Телеметрия, события, отчётность с известной задержкой | Агрегация, правила контроля | Сокращение времени на сбор картины | Ложное ощущение полноты при пропусках данных |
| Диагностический | Историческая телеметрия, журналы отказов, конфигурации | Корневой анализ, физические модели, классификация | Сокращение времени поиска причины | Ошибочная атрибуция причины, подмена корреляции причинностью |
| Предиктивный | Длинные исторические ряды, размеченные отказы, внешние факторы | Регрессия, временные ряды, физика деградации | Переход к обслуживанию по состоянию, ранние предупреждения | Ложные тревоги, дрейф модели, редкие события вне обучающей выборки |
| Предписывающий | Всё вышеперечисленное, плюс ограничения, стоимости, ресурсы | Оптимизация, сценарное моделирование, теория решений | Выбор лучшего варианта, обоснованность решений | Оптимизация не той целевой функции, скрытые ограничения |
| Автономный | Надёжный поток в реальном времени, контроль исполнения | Управление с обратной связью, безопасные политики | Скорость реакции, снятие рутинной нагрузки | Каскадные ошибки, потеря компетенции оператора, ответственность за ущерб |

## 3. Критерии перехода между уровнями

Переход на следующий уровень допустим, только когда выполнены проверяемые условия. Наиболее частая проектная ошибка — продажа предиктивного двойника на данных, которых хватает лишь на информационный уровень.

| Переход | Обязательные условия | Как проверить |
|---------|---------------------|---------------|
| Описательный → Информационный | Автоматический канал данных; известны задержка, полнота и точность; объекты однозначно идентифицированы | Сравнить состояние в двойнике с фактическим на выборке из 20–30 объектов |
| Информационный → Диагностический | Накоплена история; отказы и отклонения размечены; есть модель связи «симптом — причина» | Проверить долю случаев, где причина найдена верно, на прошлых инцидентах |
| Диагностический → Предиктивный | История покрывает достаточное число событий целевого класса; определён горизонт прогноза; задан порядок измерения точности | Ретроспективный прогноз на отложенном периоде, сравнение с фактом |
| Предиктивный → Предписывающий | Формализованы ограничения и стоимости; определена целевая функция; согласован владелец решения | Прогон исторического решения: совпала бы рекомендация с тем, что оказалось верным |
| Предписывающий → Автономный | Задан коридор автономии; есть механизм отката; журналирование воздействий; распределена ответственность | Испытания в песочнице и режим «теневого управления» без реального воздействия |

Отдельное правило: **разные подсистемы одного двойника закономерно находятся на разных уровнях**. Национальный или заводской двойник целиком редко бывает однородным. Уровень зрелости корректно указывать для сценария, а не для платформы в целом.

## 4. Типовые сценарии применения

| Отрасль | Сценарий | Реалистичный уровень | Основная метрика эффекта |
|---------|----------|----------------------|--------------------------|
| Машиностроение | Прогноз остаточного ресурса узла | Предиктивный | Снижение аварийных простоев, часы |
| Энергетика | Оценка устойчивости сети при отключении элемента | Предписывающий | Недоотпуск энергии, снижение риска каскада |
| Транспорт и логистика | Резервирование маршрутов и узлов | Предписывающий | Срок восстановления поставок, сутки |
| Нефтегаз и добыча | Мониторинг режима работы скважин и оборудования | Диагностический — предиктивный | Внеплановые остановки, добыча на единицу затрат |
| Строительство и ЖКХ | Эксплуатация здания на основе модели «как построено» | Информационный — диагностический | Затраты на обслуживание, число заявок |
| Здравоохранение (организация) | Планирование мощностей и потоков пациентов | Предиктивный | Время ожидания, загрузка коек |
| Городское управление | Оценка последствий градостроительного решения | Предписывающий | Нагрузка на инфраструктуру, транспортная доступность |
| Сельское хозяйство | Прогноз урожайности и потребности в ресурсах | Предиктивный | Отклонение прогноза от факта, затраты на гектар |
| Государственное планирование | Сравнение сценариев развития территории | Предписывающий | Скорость и обоснованность решений, выявленные дефициты |

Наблюдение: сценарии предписывающего уровня чаще встречаются там, где решение принимается редко, но стоит дорого. Сценарии предиктивного уровня — там, где решение принимается часто и связано с износом оборудования. Автономный уровень практически ограничен контурами с быстрым и обратимым воздействием.

## 5. Анкета оценки зрелости сценария

Оцените сценарий по девяти утверждениям: 0 — нет, 1 — частично, 2 — да, подтверждено.

| № | Утверждение | Балл |
|---|-------------|------|
| 1 | Объекты сценария однозначно идентифицированы и не дублируются между системами | 0–2 |
| 2 | Данные поступают автоматически, задержка измерена и приемлема для решения | 0–2 |
| 3 | Известна полнота данных: доля пропусков и её влияние на выводы | 0–2 |
| 4 | Накоплена история достаточной длины для целевых событий | 0–2 |
| 5 | Причины отклонений формализованы, а не определяются экспертно каждый раз | 0–2 |
| 6 | Точность прогноза измеряется на отложенных данных и публикуется | 0–2 |
| 7 | Ограничения, стоимости и целевая функция решения записаны явно | 0–2 |
| 8 | Назван владелец решения и периодичность его принятия | 0–2 |
| 9 | Определён порядок действий при расхождении модели и реальности | 0–2 |

Интерпретация суммы:

| Сумма баллов | Реалистично достижимый уровень | Рекомендация |
|--------------|-------------------------------|--------------|
| 0–5 | Описательный | Начать с наведения порядка в справочниках и идентификаторах |
| 6–9 | Информационный | Строить мониторинг, не обещать прогноз |
| 10–13 | Диагностический | Формализовать связь «симптом — причина» |
| 14–16 | Предиктивный | Заложить обязательное измерение точности прогноза |
| 17–18 | Предписывающий | Согласовать целевую функцию и ответственность до запуска |

Автономный уровень по анкете не выводится: он требует отдельной оценки рисков, коридора автономии и юридического распределения ответственности.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Обещать предиктивный уровень на данных информационного | Прогноз лучше продаётся, чем мониторинг | Проверять длину истории и наличие размеченных событий до старта |
| Присваивать уровень зрелости платформе целиком | Удобно для отчётности и презентаций | Указывать уровень для каждого сценария отдельно |
| Пропускать диагностический уровень | Кажется промежуточным и неинтересным | Без формализации причин прогноз не объясним и не принимается пользователем |
| Не измерять точность прогноза | Отсутствует регламент проверки постфактум | Заложить ретроспективную проверку как обязательную функцию, а не как исследование |
| Переходить к автономии без коридора и отката | Технически автоматизация проще, чем её ограничение | Сначала теневое управление, затем узкий коридор с журналом воздействий |
| Оптимизировать неверную целевую функцию | Целевая функция берётся из доступных метрик, а не из интересов заказчика | Согласовать целевую функцию и ограничения письменно до разработки |
| Считать зрелость характеристикой ПО | Вендор описывает возможности продукта, а не внедрения | Оценивать зрелость по данным, моделям и принимаемым решениям |

## Пример: «Цифровой двойник России»

Проект даёт наглядный пример неоднородной зрелости. Согласно [MVP](../../MVP.md), минимальная версия сознательно ограничена: в неё входят «региональный паспорт, поиск дефицитов, простые прогнозы и сравнение сценариев», а «полная автоматизация принятия решений» и «точное реальновременное моделирование всех физических процессов» вынесены за границы MVP. Это означает целевой диапазон уровней от описательного до предписывающего с явным отказом от автономного.

| Функция MVP | Уровень зрелости | Комментарий |
|-------------|------------------|-------------|
| Региональный паспорт: карта ресурсов, мощностей, узлов, вакансий | Описательный — информационный | Основа: единые справочники и правила геокодирования |
| Поиск дефицитов и тепловые карты рисков | Диагностический | Отклонение сопоставляется с причиной: нехватка кадров, мощности, связности |
| Оценка кадрового дефицита при запуске нового производства | Предиктивный | Прогноз потребности, а не факт |
| Сравнение площадок и сценариев «как есть» / «после проекта» | Предписывающий | Выбор варианта с оценкой последствий |

Критерии перехода в проекте заданы через требования к данным и моделям. [MVP](../../MVP.md) требует, чтобы каждая модель сопровождалась описанием допущений, входных данных и ограничений применимости, версионировалась вместе с наборами данных, а результат сопровождался доступной пользователю цепочкой расчёта; спорные сценарии проверяются минимум на двух независимых наборах допущений. По сути это дисциплина, без которой предиктивный и предписывающий уровни недостоверны.

В [Тезисах](../../Тезисы.md) отдельно зафиксирована потребность в воспроизводимости аналитики: непрозрачные и плохо повторяемые расчёты порождают недоверие к выводам моделей. Для государственного контура это ограничение сильнее, чем в промышленности: там, где отраслевой двойник может позволить себе «чёрный ящик» с хорошей статистикой, решение органа власти должно быть объяснимо.

## Практическое задание

**Задание 1.2.** Для объекта своего сквозного проекта постройте дорожную карту зрелости.

1. Заполните анкету из раздела 5 и получите балл; приложите обоснование каждой оценки одной строкой.
2. Определите текущий уровень зрелости и целевой уровень на горизонте 12 месяцев.
3. Для перехода на следующий уровень выпишите обязательные критерии из раздела 3 и укажите, какие из них не выполнены.
4. Составьте таблицу «уровень → данные → модели → эффект → риски» для целевого уровня применительно к вашему объекту.
5. Опишите один сценарий применения и укажите метрику, по которой будет измеряться эффект.

Критерии приёмки:

- [ ] Анкета заполнена целиком, каждая оценка обоснована фактом, а не намерением
- [ ] Текущий уровень определён по признакам из раздела 1, а не по названию используемого ПО
- [ ] Целевой уровень отличается от текущего не более чем на один шаг
- [ ] Для каждого невыполненного критерия перехода указано конкретное действие и ответственный
- [ ] В таблице рисков есть хотя бы один риск, специфичный для вашего объекта, а не общий
- [ ] Метрика эффекта измерима и имеет базовое значение «до»
- [ ] Явно указано, какие подсистемы останутся на более низком уровне и почему это допустимо

## Проверочные вопросы

1. Назовите шесть уровней зрелости и вопрос, на который отвечает каждый.
2. Почему нельзя перейти к предиктивному уровню, не имея размеченной истории отказов?
3. Какой признак отличает достигнутый диагностический уровень от заявленного?
4. Что такое коридор автономии и почему без него автономный уровень недопустим?
5. Может ли одна платформа одновременно работать на информационном и предписывающем уровнях? Приведите пример.
6. Какие два элемента MVP «Цифрового двойника России» явно вынесены за границы минимальной версии и как это связано с уровнями зрелости?
7. Почему для государственных сценариев требование объяснимости модели строже, чем для промышленных?
