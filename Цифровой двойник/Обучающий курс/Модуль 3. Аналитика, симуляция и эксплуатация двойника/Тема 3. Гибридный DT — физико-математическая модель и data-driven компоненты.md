# Модуль 3. Тема 3. Гибридный DT — физико-математическая модель и data-driven компоненты

> Модуль 3 «Аналитика, симуляция и эксплуатация двойника» · Тема 3 из 7

## Учебные цели

После изучения темы студент сможет:

- объяснить, почему чисто физическая и чисто статистическая модели по отдельности недостаточны для эксплуатационного двойника;
- выбрать схему гибридизации (признаки из физики, коррекция остатка, суррогатная модель, PINN, идентификация параметров, ансамбль) под задачу и доступные данные;
- сформулировать требования к обучающим данным: объём, покрытие режимов, разметка, качество;
- распознать дрейф данных и переобучение и назначить процедуру реакции;
- спроектировать MLOps-контур двойника с версионированием данных, моделей и мониторингом качества.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Физико-математическая модель | Расчёт на основе законов сохранения, уравнений состояния и конструктивных параметров объекта |
| Data-driven модель | Зависимость, полученная из наблюдаемых данных без явного описания механизма |
| Гибридная модель | Комбинация обоих подходов в одном расчётном контуре |
| ROM (reduced order model) | Суррогатная модель пониженного порядка, воспроизводящая поведение тяжёлого расчёта за доли секунды |
| PINN | Нейросеть, в функцию потерь которой добавлена невязка физических уравнений |
| Невязка (остаток) | Разность между фактом и расчётом физической модели |
| Дрейф данных | Изменение распределения входов относительно обучающей выборки |
| Дрейф концепции | Изменение самой зависимости «вход — выход» (износ, реконструкция, смена сырья) |
| MLOps | Практики управления жизненным циклом моделей: версии, воспроизводимость, выкладка, мониторинг |
| Lineage данных | Прослеживаемая цепочка происхождения значения от источника до результата |

## Почему ни один подход не самодостаточен

| Свойство | Чистая физика | Чистый ML |
|----------|---------------|-----------|
| Данные для построения | Конструктив, характеристики, справочники | Большая размеченная история |
| Поведение вне наблюдённых режимов | Экстраполирует по закону | Экстраполирует непредсказуемо |
| Интерпретируемость | Высокая, есть причинное объяснение | От средней до нулевой |
| Учёт неописанных эффектов (загрязнение, износ, человеческий фактор) | Не учитывает | Улавливает, если они были в данных |
| Скорость расчёта | Часто медленно (CFD, МКЭ) | Быстро после обучения |
| Стоимость сопровождения | Перекалибровка параметров | Переобучение, контроль дрейфа |
| Поведение при смене объекта | Переносится с пересчётом параметров | Требует новых данных |

Физическая модель систематически ошибается там, где реальность богаче уравнений: отложения на теплообменных поверхностях, износ, нештатные режимы, поведение персонала. Статистическая модель ошибается там, где не было данных: новый режим, редкая авария, изменившийся объект. Эксплуатационный двойник живёт именно в этом пересечении, поэтому гибридизация — норма, а не исключение.

## Схемы гибридизации

| Схема | Как устроена | Когда применять | Риск |
|-------|--------------|-----------------|------|
| Физика как признаки | Выходы физрасчёта (КПД, число Рейнольдса, баланс) подаются на вход ML-модели | Много данных, нужна интерпретируемость признаков | Ошибка физики переносится в признаки |
| Коррекция остатка | ML обучается на невязке `факт − физика` и добавляется к расчёту | Физика верна по структуре, но смещена | При дрейфе поправка «съедает» физику |
| Суррогат (ROM) | ML обучается воспроизводить тяжёлый расчёт | Нужен отклик в реальном времени, оптимизация, Монте-Карло | Действует только в области обучения |
| PINN | Физические уравнения включены в функцию потерь | Мало данных, известны уравнения | Сложность обучения, чувствительность к постановке |
| Идентификация параметров | ML оценивает параметры физической модели по данным | Параметры меняются во времени (загрязнение, износ) | Смещение параметров маскирует дефект |
| Ансамбль | Несколько моделей, агрегация с весами по надёжности | Спорные и критичные расчёты | Усложнение объяснения результата |

```
                +----------------------+
входы --------> | физическая модель    | --> базовый расчёт
   |            +----------------------+          |
   |                                              +--> ( + ) --> итог
   |            +----------------------+          |
   +----------> | ML-модель остатка    | --> поправка
                +----------------------+
                            ^
                            |
                 контроль: |поправка| / |расчёт| < порог
```

Правило контроля для схемы коррекции остатка: если модуль поправки превышает установленную долю базового расчёта (например, 15 процентов), это сигнал не о точности, а о том, что физическая модель перестала описывать объект. Такой случай направляется на перекалибровку физики, а не на переобучение поправки.

Учебный пример выбора. Задача — оценить пропускную способность участка сети при отказе элемента для расчёта в реальном времени. Полный физический расчёт занимает 4 минуты, а пользователю нужен ответ за 2 секунды при переборе 200 вариантов отказа. Прямой перебор — 13 часов. Решение: обучить суррогат на 5 000 заранее посчитанных вариантов, довести отклик до 20 миллисекунд, а для итогового варианта, выбранного пользователем, запускать точный расчёт как подтверждение. Это стандартная связка «быстрый суррогат для перебора — точная модель для решения».

## Требования к данным для обучения

| Требование | Содержание | Как проверять |
|------------|------------|---------------|
| Объём | Достаточен для сложности модели; для редких событий важен не общий объём, а число примеров события | Число наблюдений на класс и на режим |
| Покрытие режимов | Данные должны включать все режимы, в которых модель будет применяться | Матрица «режим × число наблюдений», пустые клетки — зона запрета |
| Разметка | Известны факты отказов, ремонтов, замен, изменений конструкции | Сверка с журналами работ |
| Временное выравнивание | Метки времени согласованы между источниками | Проверка задержек и рассинхронизации |
| Качество | Известны пропуски, выбросы, участки с неисправными датчиками | Доля пропусков, флаги качества |
| Отсутствие утечки цели | Во входах нет величин, доступных только после наступления события | Ревизия признаков вручную |

Утечка цели — самая частая причина «отличных» результатов, которые рассыпаются в эксплуатации. Пример: признак «код ремонтной заявки» отлично предсказывает отказ, но заявка создаётся уже после обнаружения дефекта, то есть в момент прогноза недоступна.

Разделение выборки во временных задачах выполняется строго по времени: обучение на раннем периоде, проверка на позднем. Случайное перемешивание временного ряда даёт завышенную оценку качества, потому что модель фактически подглядывает в будущее.

## Дрейф и переобучение

| Явление | Проявление | Реакция |
|---------|------------|---------|
| Дрейф данных | Распределение входов сместилось, качество пока держится | Расширить обучающую выборку, следить за метрикой |
| Дрейф концепции | Ошибка растёт при неизменных входах | Переобучение, пересмотр признаков |
| Сезонность | Циклическое ухудшение в определённые периоды | Добавить сезонные признаки или отдельные модели |
| Переобучение | Ошибка на обучении мала, на проверке велика | Упрощение модели, регуляризация, больше данных |
| Деградация признака | Один датчик вышел из строя, признак стал константой | Контроль качества входов до расчёта |

Индикаторы для мониторинга: расхождение распределений входов (например, по статистике Колмогорова — Смирнова или индексу стабильности популяции), доля входов вне обучающего диапазона, скользящая ошибка на размеченных фактах, доля отказов модели от расчёта.

Учебный пример. Модель прогноза нагрузки обучена на данных 2024 года, MAPE на проверке — 3,8 процента. Через восемь месяцев эксплуатации скользящий MAPE вырос до 6,9 процента. Проверка показала: 22 процента входных наблюдений выходят за диапазон обучающей выборки по признаку «температура наружного воздуха», поскольку зима оказалась холоднее исторической. Это дрейф данных, а не концепции: правильная реакция — дообучение на расширенном диапазоне, а не смена архитектуры модели.

## MLOps-контур цифрового двойника

```
[источники] -> [версионированный набор данных] -> [обучение] -> [реестр моделей]
     ^                     |                                          |
     |                     v                                          v
[контроль качества]  [валидация: точность, границы]  ---->  [выкладка в контур эксплуатации]
     ^                                                              |
     |                                                              v
[мониторинг дрейфа и ошибки] <-------------------------- [расчёты и обратная связь]
     |
     +--> триггер переобучения / перекалибровки / вывода модели из эксплуатации
```

Минимальный состав артефактов, без которых двойник неуправляем:

| Артефакт | Что фиксирует |
|----------|---------------|
| Версия набора данных | Срез, период, фильтры, источники, хеш |
| Версия кода подготовки признаков | Одинаковая логика при обучении и в эксплуатации |
| Версия модели | Параметры обучения, метрики, дата, автор |
| Паспорт модели | Назначение, границы применимости, метрики, ограничения (см. тему 6) |
| Журнал расчётов | Кто, когда, на какой версии модели и данных получил результат |
| Регламент реакции | Пороги метрик, при которых модель переобучается или выводится из эксплуатации |

Ключевое требование к эксплуатации — идентичность обработки признаков при обучении и при расчёте. Расхождение (training-serving skew) даёт ошибки, которые невозможно объяснить по метрикам обучения: модель корректна, а на вход ей поступают признаки, посчитанные иначе.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| ML вместо физики там, где физика известна | Данные проще, чем инженерная модель | Использовать физику как каркас, ML — как поправку |
| Суррогат применяется вне области обучения | Модель формально считает любой вход | Проверка принадлежности входа обучающей области перед выдачей |
| Случайное разделение временного ряда | Привычка из задач классификации | Разделение строго по времени |
| Утечка цели в признаках | Признаки собираются автоматически из витрины | Ручная ревизия происхождения каждого признака |
| Поправка ML маскирует деградацию объекта | Модель остатка подстраивается под износ | Контроль величины поправки как отдельного индикатора |
| Модель без паспорта и версии | Быстрое прототипирование ушло в эксплуатацию | Запрет выкладки без паспорта и записи в реестр |
| Переобучение по расписанию без проверки | Автоматизация ради автоматизации | Переобучение по триггеру метрики с обязательной валидацией перед выкладкой |

## Пример: «Цифровой двойник России»

В [Тезисах](../../Тезисы.md) прямо зафиксированы два принципа моделирования, которые задают требования к гибридному контуру: модели версионируются вместе с данными, на которых обучены, а спорные сценарии проверяются на нескольких независимых моделях. Первый принцип — это требование к MLOps-контуру (связка «версия данных — версия модели» как единый артефакт), второй — прямое указание на ансамблевую схему для критичных расчётов.

Пятый контур системы, исследовательский, по [Примерам обработки информации для контуров](../../Примеры%20обработки%20информации%20для%20контуров.md) работает на синтетических, тестовых и обезличенных наборах, а в продуктивные контуры передаёт модели, методики и отчёты о качестве, но не обучающие наборы с чувствительными сведениями. Для гибридного двойника это означает особую организацию цикла: обучение и эксперименты идут на обезличенных данных, а в ведомственный или инфраструктурный контур переносится артефакт модели с паспортом и отчётом о качестве. Отсюда следует практическое требование — качество, измеренное на обезличенном наборе, необходимо подтверждать повторно уже в целевом контуре, поскольку обезличивание и агрегация меняют распределение данных.

В [Описании](../../Описание.md) режим обновления заявлен как диапазон «от периодических обновлений из реестров до потоковых данных с датчиков и отраслевых систем». Разная периодичность источников — самостоятельная причина дрейфа: модель, обученная на связке ежесуточных и годовых показателей, при переходе источника на потоковый режим получает вход с другими статистическими свойствами.

## Практическое задание

Постройте гибридный расчётный узел для сквозного проекта.

1. Опишите имеющуюся физическую (или балансовую) модель объекта и перечислите эффекты, которые она не учитывает.
2. Выберите схему гибридизации из таблицы темы и обоснуйте выбор через доступные данные, требуемую скорость и потребность в интерпретируемости.
3. Соберите или сгенерируйте обучающий набор, постройте матрицу покрытия режимов и отметьте зоны запрета.
4. Обучите data-driven компонент, разделив выборку по времени, и сравните три варианта: только физика, только ML, гибрид.
5. Опишите MLOps-контур: перечень версионируемых артефактов, метрики мониторинга, триггеры переобучения.

Критерии приёмки:

- [ ] перечислены конкретные эффекты, не описываемые физической моделью;
- [ ] выбор схемы гибридизации обоснован тремя факторами, а не общими словами;
- [ ] построена матрица покрытия режимов с указанием пустых клеток;
- [ ] выборка разделена по времени, а не случайно;
- [ ] приведено сравнение трёх вариантов по одинаковой метрике на одном проверочном периоде;
- [ ] проведена ревизия признаков на утечку цели с письменным выводом;
- [ ] задан контроль величины ML-поправки относительно базового расчёта;
- [ ] определены пороги метрик и триггеры переобучения и вывода модели из эксплуатации.

## Проверочные вопросы

1. В каких ситуациях чисто физическая модель систематически ошибается, а в каких — чисто статистическая?
2. Чем схема коррекции остатка отличается от схемы идентификации параметров по последствиям для диагностики?
3. Зачем суррогатной модели контроль принадлежности входа обучающей области?
4. Что такое утечка цели и почему её не видно по метрикам качества на исторических данных?
5. Как отличить дрейф данных от дрейфа концепции и почему реакция на них разная?
6. Что такое training-serving skew и чем он опасен?
7. Какие артефакты обязательно версионируются в MLOps-контуре двойника и почему без них модель неуправляема?
