# Модуль 3. Тема 4. Визуализация и интерфейсы

> Модуль 3 «Аналитика, симуляция и эксплуатация двойника» · Тема 4 из 7

## Учебные цели

После изучения темы студент сможет:

- проектировать интерфейс двойника по цепочке «задача роли → вопрос → представление», а не от доступных данных;
- подобрать тип представления (карта, 3D-сцена, мнемосхема, дашборд, временной ряд, граф, таблица) под класс вопроса;
- отобразить неопределённость расчёта и качество исходных данных так, чтобы пользователь не принял оценку за факт;
- спроектировать систему алармов с приоритетами и подавлением шума;
- задать требования к API как к машинному интерфейсу и провести приёмку интерфейса по чек-листу.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Роль пользователя | Типовой пользователь с определённым набором задач, полномочий и горизонтом решений |
| Уровень детализации | Глубина раскрытия данных, соответствующая задаче роли |
| Мнемосхема | Схематическое изображение технологического процесса с текущими значениями |
| Дашборд | Компоновка показателей, отвечающая на фиксированный набор вопросов без прокрутки |
| Drill-down | Переход от агрегата к составляющим его данным |
| Аларм | Сигнал, требующий действия оператора, с приоритетом и предписанной реакцией |
| Шум алармов | Поток сигналов, превышающий способность оператора их обрабатывать |
| Индикатор качества данных | Признак свежести, полноты и достоверности отображаемого значения |
| API | Программный интерфейс — способ получения данных двойника без графического экрана |
| Цветовая доступность | Свойство схемы оставаться читаемой при нарушениях цветовосприятия |

## Принцип проектирования: задача — вопрос — представление

Интерфейс проектируется от решения, а не от данных. Порядок обратный привычному: сначала фиксируется, какое действие совершает пользователь, затем какой вопрос требует ответа перед этим действием, и лишь потом — какое представление отвечает на вопрос быстрее всего.

| Роль | Решение | Вопрос | Представление | Горизонт |
|------|---------|--------|---------------|----------|
| Оператор | Вмешаться в режим сейчас | Что не так и что делать | Мнемосхема, список активных алармов | Секунды — минуты |
| Инженер | Найти причину отклонения | Почему показатель ушёл | Временные ряды с наложением расчёта, остатки модели | Часы — недели |
| Аналитик | Сравнить варианты | Какой сценарий лучше и насколько устойчив | Таблица сценариев, распределения, чувствительность | Недели — годы |
| Руководитель | Утвердить решение и ресурсы | Где риск, чего не хватает, какова цена | Карта, сводный дашборд, отчёт с выводом | Кварталы — годы |

Одни и те же данные для этих ролей выглядят по-разному, и попытка сделать «один экран для всех» приводит к тому, что оператор тонет в стратегической аналитике, а руководитель — в потоке измерений.

## Типы представлений и их назначение

| Тип | На какой вопрос отвечает | Сильная сторона | Когда неуместен |
|-----|--------------------------|-----------------|-----------------|
| Карта / ГИС | Где это происходит | Пространственные связи, охват, плотность | Вопрос не имеет географической природы |
| 3D-сцена | Как объект устроен, что где физически расположено | Осмотр конструкции, коллизии, обходы | Требуется сравнение чисел |
| Мнемосхема | В каком состоянии процесс прямо сейчас | Мгновенное считывание оператором | Ретроспективный анализ |
| Дашборд KPI | Всё ли в норме по ключевым показателям | Быстрая свёртка состояния | Поиск причины |
| Временной ряд | Как менялось и куда движется | Тренды, корреляция событий, наложение расчёта | Обзор десятков объектов сразу |
| Граф связей | От чего это зависит и на что влияет | Каскадные отказы, цепочки поставок | Точные количественные сравнения |
| Таблица | Точные значения и сортировка | Выгрузка, сверка, работа со списками | Быстрая оценка ситуации |
| Отчёт | Что решено и на каком основании | Фиксация, согласование, аудит | Оперативная работа |

Частая ошибка проектов двойников — избыточная 3D-визуализация. Трёхмерная сцена эффектна на демонстрации, но для большинства эксплуатационных вопросов («какая задвижка перегрета», «где узкое место») мнемосхема или таблица дают ответ быстрее и дешевле.

## Правила проектирования дашборда

1. Один дашборд — один вопрос или одна связная группа вопросов конкретной роли.
2. Главный показатель занимает верхнюю левую зону; порядок чтения соответствует порядку принятия решения.
3. Число одновременно отображаемых показателей ограничено: 5–9 на экран для оперативных панелей.
4. Каждое число сопровождается точкой отсчёта: план, норматив, прошлый период или порог. Число без сравнения не информативно.
5. Единицы измерения, период и дата актуальности видны без наведения курсора.
6. Любой агрегат допускает drill-down до исходных данных не более чем за три перехода.
7. Отсутствие данных отображается явно и отличается от нулевого значения.

```
+-------------------------------------------------------------+
| Состояние объекта: НОРМА   | данные на 14:32, задержка 40 с   |
+---------------------------+---------------------------------+
| Главный KPI: 87 % (план 90 %)  | Тренд 24 ч  /\_/\__          |
+---------------------------+---------------------------------+
| Активные алармы: 2 (крит. 0)   | Качество данных: 3 датчика  |
|  - Перепад T выше нормы        | без связи > 10 мин          |
|  - Дрейф расходомера F-12      |                             |
+---------------------------+---------------------------------+
| Прогноз на 8 ч: 84 % (интервал 79-89 %)                      |
+-------------------------------------------------------------+
```

## Отображение неопределённости и качества данных

Расчёт двойника — оценка, а не измерение. Если интерфейс показывает прогноз одним числом, пользователь неизбежно воспринимает его как факт и принимает решения без запаса.

| Что показываем | Приём | Пример подписи |
|----------------|-------|----------------|
| Интервал прогноза | Полоса вокруг линии, указание перцентилей | «84 %, интервал 79–89 % (P10–P90)» |
| Источник значения | Пометка «измерено / расчёт / оценка / план» | «Расчёт модели v3.2» |
| Свежесть | Возраст данных и порог устаревания | «Данные на 14:32, задержка 40 с» |
| Полнота | Доля пропусков в периоде | «Покрытие периода 92 %» |
| Достоверность | Флаг качества датчика и результата валидации | «Датчик F-12: подозрение на дрейф» |
| Выход за область валидности | Явное предупреждение вместо тихой выдачи числа | «Вне области применимости модели» |

Правило: если результат получен за пределами области валидности модели, интерфейс обязан отказать в выдаче или пометить результат предупреждением. Тихая экстраполяция — источник самых дорогих ошибок доверия (тема 6).

**Цветовая доступность.** Цвет не должен быть единственным носителем смысла: критичность дублируется формой значка, текстом и положением в списке. Ограничение палитры состояний тремя-четырьмя цветами и проверка на распространённых типах дальтонизма — минимальное требование. Красный резервируется исключительно для состояний, требующих действия, иначе он перестаёт восприниматься.

## Алармы и уведомления

| Приоритет | Смысл | Требуемая реакция | Канал |
|-----------|-------|-------------------|-------|
| Критический | Угроза безопасности, отказ функции | Немедленно | Звук, всплывающее окно, дублирование |
| Высокий | Развитие дефекта, риск отказа в ближайшее время | В течение смены | Панель, уведомление ответственному |
| Средний | Отклонение от нормы без непосредственного риска | В течение суток | Список, сводка |
| Информационный | Событие для протокола | Не требуется | Журнал |

Каждый аларм обязан содержать четыре элемента: что произошло, где, насколько серьёзно, что делать. Сигнал без предписанного действия персонал со временем игнорирует.

**Подавление шума алармов.** Практические приёмы:

- гистерезис и минимальная длительность отклонения — против дребезга на границе уставки;
- подавление зависимых сигналов: при отключении узла глушатся все производные тревоги от его датчиков;
- группировка каскадных срабатываний в одно событие с раскрываемым составом;
- временное маскирование на период плановых работ с обязательным журналированием;
- регулярная ревизия: сигналы, которые ни разу не привели к действию за квартал, пересматриваются.

Учебный пример. За сутки на панель поступило 940 сигналов, из них 610 — от одного узла в состоянии ремонта, 180 — дребезг двух датчиков на границе уставки. После маскирования ремонтируемого узла и введения задержки подтверждения 60 секунд поток снизился до 150 сигналов в сутки, из которых 12 привели к действиям. До изменения оператор физически не мог просмотреть поток и пропускал значимые события — типичная картина, когда формально «все тревоги настроены», а фактически диагностика не работает.

## API как интерфейс без экрана

Значительная часть потребителей двойника — не люди, а системы: отчётные модули, смежные информационные системы, модели других организаций. Требования к машинному интерфейсу формулируются так же строго, как к экранному.

| Требование | Содержание |
|------------|------------|
| Контракт | Схема ответа зафиксирована и версионирована; несовместимые изменения — только через новую версию |
| Метаданные | Каждое значение сопровождается временем, единицами, источником, признаком качества |
| Пагинация и лимиты | Ограничение объёма выдачи и частоты запросов, предсказуемое поведение при превышении |
| Идемпотентность и повтор | Повторный запрос не искажает данные, определено поведение при обрыве |
| Права доступа | Область видимости определяется ролью и контуром, а не параметрами запроса |
| Журналирование | Фиксируется, кто, когда и какой объём данных получил |

Требования к отклику и объёму задаются по классу сценария:

| Класс | Целевой отклик | Типичный объём | Пример |
|-------|----------------|----------------|--------|
| Оперативный экран | до 1–2 с | десятки значений | Мнемосхема, активные алармы |
| Аналитический запрос | до 10–30 с | тысячи строк | Сравнение периодов |
| Сценарный расчёт | минуты, с индикацией прогресса | серия прогонов | What-if по теме 1 |
| Массовая выгрузка | асинхронно, по готовности | миллионы строк | Годовой срез для внешней системы |

Смешивать классы в одном интерфейсном контуре нельзя: тяжёлая выгрузка, выполненная синхронно, блокирует оперативную панель.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Интерфейс спроектирован от данных, а не от решения | Начинают с того, что уже есть в хранилище | Начинать с перечня решений роли |
| Один экран для всех ролей | Экономия на разработке | Разделять по ролям и горизонту решений |
| Прогноз показан одним числом | Так «понятнее» | Всегда выводить интервал и источник значения |
| Цвет — единственный носитель смысла | Не проверялась доступность | Дублировать формой, текстом, порядком |
| Красный цвет для любых отклонений | Нет дисциплины приоритетов | Красный — только для требующих действия |
| Поток алармов, не обрабатываемый оператором | Каждый датчик получил тревогу «на всякий случай» | Подавление зависимых сигналов, ревизия по факту действий |
| Отсутствие данных выглядит как ноль | Дефолтное поведение библиотеки | Явное отображение пропуска |
| API отдаёт значения без метаданных | Интерфейс делали «для себя» | Метаданные качества и происхождения обязательны в контракте |

## Пример: «Цифровой двойник России»

В [Описании](../../Описание.md) интерфейс системы определён как «карта/3D-модель, аналитические панели, отчёты, API для разрешённых наборов данных» — то есть все четыре класса представлений из этой темы присутствуют в целевой архитектуре. Там же в принципах реализации зафиксировано требование «фиксировать происхождение данных, качество, дату обновления и права доступа». Это прямое обязательство интерфейса: каждое отображаемое значение сопровождается источником, качеством и датой актуальности, а не подаётся как обезличенное число.

Ключевое отличие проекта сформулировано в том же документе как переход от «карты объектов» к «модели действий»: пользователь должен получать ответ, какие решения доступны, какие последствия вероятны, какие ограничения мешают. С точки зрения проектирования интерфейса это означает, что карта — не конечный продукт, а точка входа: с объекта на карте должен открываться сценарный расчёт и перечень ограничений, иначе система остаётся геопорталом.

Пример открытого контура из [Примеров обработки информации для контуров](../../Примеры%20обработки%20информации%20для%20контуров.md) показывает интерфейсный результат одного и того же расчёта в трёх формах: слой карты «вакансии и обучение», открытый API с агрегированными показателями и PDF-паспорт «рынок труда муниципалитета». Существенно, что интерфейс здесь несёт функцию защиты: зарплатные вилки округляются до диапазонов, а категории, где менее N работодателей, скрываются. То есть правила отображения — часть контура безопасности, а не только удобства (тема 7).

Из [Сценариев](../../Сценарии.md) видно, что форма результата задаётся в постановке сценария наравне с данными: «интерактивный паспорт региона», «таблица сценариев с показателями», «карта программ с подсветкой конкуренции за ресурсы и сроки». Это верная практика — тип представления фиксируется в требованиях, а не выбирается разработчиком на этапе реализации.

## Практическое задание

Спроектируйте интерфейсный слой сквозного проекта.

1. Определите три роли пользователей и для каждой перечислите по два-три решения, которые она принимает.
2. Постройте таблицу «роль → решение → вопрос → представление → требуемый отклик».
3. Разработайте макет одного дашборда (схема в тексте или изображение) для оперативной роли: не более девяти показателей, каждый с точкой отсчёта.
4. Задайте систему алармов: не менее пяти сигналов с приоритетом, условием срабатывания, условием снятия и предписанным действием.
5. Опишите контракт API для одного набора данных: поля, метаданные качества, лимиты, права доступа.

Критерии приёмки:

- [ ] для каждой роли указаны решения, а не «потребности в информации»;
- [ ] каждый элемент дашборда отвечает на конкретный вопрос из таблицы;
- [ ] все прогнозные значения показаны с интервалом и пометкой источника;
- [ ] отображены свежесть и полнота данных, отсутствие данных отличимо от нуля;
- [ ] цвет не является единственным носителем смысла;
- [ ] каждый аларм содержит условие срабатывания, условие снятия и предписанное действие;
- [ ] предусмотрены меры подавления шума алармов;
- [ ] контракт API включает метаданные качества, лимиты и правила доступа;
- [ ] заданы целевые времена отклика по классам сценариев.

## Проверочные вопросы

1. Почему проектирование интерфейса начинается с решения, а не с состава данных?
2. В каких случаях 3D-сцена уступает мнемосхеме или таблице?
3. Какие пять признаков качества данных должен нести отображаемый показатель?
4. Почему прогноз, показанный одним числом, опасен для принятия решений?
5. Какие четыре элемента обязан содержать аларм?
6. Назовите три приёма подавления шума алармов и объясните механику каждого.
7. Чем требования к API отличаются от требований к экранному интерфейсу и что у них общего?

## Источники

- [ISO 23247 «Digital twin framework for manufacturing»](https://www.iso.org/standard/75066.html) — в части представления данных и интерфейсов сущностей двойника.
- [ISO/IEC 30173:2023 «Digital twin — Concepts and terminology»](https://www.iso.org/standard/81442.html)
- ISO 13374 — часть серии посвящена представлению результатов мониторинга состояния и обмену ими между компонентами.
- ISO 9241 — серия стандартов по эргономике взаимодействия человека и системы.
- [Digital Twin Consortium](https://www.digitaltwinconsortium.org/) — отраслевые материалы по визуализации и пользовательским сценариям двойников.
- [ГОСТ Р 57700.37-2021 «Цифровые двойники изделий. Общие положения»](https://www.gostinfo.ru/catalog/Details/?id=6869870)
