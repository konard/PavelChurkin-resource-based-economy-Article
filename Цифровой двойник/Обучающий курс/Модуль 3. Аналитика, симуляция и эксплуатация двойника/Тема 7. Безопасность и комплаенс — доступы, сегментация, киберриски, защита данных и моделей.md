# Модуль 3. Тема 7. Безопасность и комплаенс — доступы, сегментация, киберриски, защита данных и моделей

> Модуль 3 «Аналитика, симуляция и эксплуатация двойника» · Тема 7 из 7

## Учебные цели

После изучения темы студент сможет:

- построить модель угроз цифрового двойника по объектам защиты: данные, модели, каналы, интерфейсы, цепочка поставок;
- распознавать специфические для двойников риски — агрегацию, инференс-атаки, отравление данных, кражу и подмену модели;
- проектировать сегментацию на зоны и каналы и определять правила передачи между контурами;
- задавать ролевой и атрибутный доступ, минимизацию и обезличивание данных, аудит действий;
- проводить предзапусковую проверку безопасности двойника по чек-листу и учитывать требования комплаенса.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Модель угроз | Систематизированное описание того, что защищаем, от кого и какими мерами |
| Зона и канал | Группа активов с общими требованиями безопасности и контролируемое соединение между зонами (подход IEC 62443) |
| Однонаправленный шлюз | Устройство, физически допускающее передачу данных только в одну сторону |
| RBAC | Управление доступом на основе ролей |
| ABAC | Управление доступом на основе атрибутов пользователя, объекта и контекста |
| Минимизация данных | Обработка только тех сведений, которые необходимы для заявленной цели |
| Обезличивание | Обработка, после которой сведения нельзя соотнести с конкретным субъектом без дополнительной информации |
| Агрегационный риск | Возникновение чувствительного результата из совокупности несекретных данных |
| Инференс-атака | Восстановление скрытых сведений по ответам системы или модели |
| Отравление данных | Внесение искажений в обучающую выборку с целью изменить поведение модели |
| Аудит действий | Неизменяемая запись обращений и операций пользователей и систем |

## Модель угроз цифрового двойника

Двойник расширяет поверхность атаки по сравнению с обычной информационной системой: он агрегирует данные многих источников, содержит модели как самостоятельную ценность и может влиять на физический объект.

| Объект защиты | Что теряется при компрометации | Пример угрозы |
|---------------|-------------------------------|---------------|
| Данные о состоянии | Конфиденциальность, целостность | Утечка телеметрии, раскрывающей режимы объекта |
| Модели и артефакты | Интеллектуальная собственность, доверие | Кража обученной модели, подмена версии в реестре |
| Каналы сбора | Целостность, доступность | Подмена значений датчиков, обрыв потока |
| Интерфейсы и API | Конфиденциальность, доступность | Массовая выгрузка через легальный доступ |
| Контур управления | Безопасность физического объекта | Навязывание вредоносной уставки |
| Цепочка поставок | Всё перечисленное | Уязвимость в стороннем компоненте или библиотеке |
| Учётные записи и права | Всё перечисленное | Избыточные права, неотозванный доступ уволенного сотрудника |

Актуальные нарушители ранжируются по возможностям: внешний неквалифицированный, внешний целевой (в том числе с ресурсами уровня государства), внутренний с легальным доступом, подрядчик и поставщик компонентов. Для большинства практических систем именно внутренний легальный доступ и подрядчик дают наибольший реализуемый риск, поскольку не требуют преодоления периметра.

## Специфические риски двойников

**Агрегация.** Отдельные наборы данных несекретны, а их сопоставление даёт чувствительный результат. Открытые сведения о размещении производств, объёмах перевозок, потреблении энергии и графиках работы в совокупности восстанавливают загрузку и зависимости объекта. Это не гипотеза, а прямое следствие назначения двойника — связывать слои. Меры: оценка агрегационного риска для каждой публикуемой связки слоёв (а не для слоя по отдельности), обобщение координат, округление и загрубление, задержка публикации, пороги подавления малых групп.

**Инференс-атака через API.** Пользователь с легальным ограниченным доступом серией запросов восстанавливает скрытые значения. Классический пример: если агрегат подавляется при менее чем пяти объектах, разность двух разрешённых выборок, отличающихся на один объект, раскрывает его данные. Меры: контроль дифференциальных запросов, ограничение частоты и объёма, фиксация минимального размера группы на всех срезах, добавление шума в агрегаты, журналирование и профилирование поведения потребителей.

**Отравление данных и моделей.** Постепенное внесение искажений в поток телеметрии смещает калибровку и обучение так, что модель начинает считать аномалию нормой. Атака особенно опасна для двойников, потому что переобучение обычно автоматизировано. Меры: валидация входов до обучения, контроль распределений, обучение только на данных из доверенных источников с подтверждённым происхождением, ручное утверждение выкладки модели, сохранение предыдущей версии для отката.

**Кража модели.** Модель извлекается прямым доступом к артефакту либо восстанавливается по большому числу запросов к API. Меры: хранение артефактов в защищённом реестре с контролем доступа, ограничение частоты запросов, отказ от выдачи избыточной детализации в ответах, водяные знаки и контроль распространения.

**Подмена телеметрии.** Ложные значения приводят к неверной диагностике и, при замкнутом контуре, к неверному воздействию. Меры: аутентификация источников, подпись или контроль целостности потока, кросс-проверка по физическим балансам и резервным измерениям, отказ от автоматических режимов при недостоверных входах (см. тему 5).

**Компрометация контура управления.** Наиболее тяжёлый сценарий: воздействие на физический объект. Меры: строгая сегментация, однонаправленная передача из технологического контура в аналитический, независимая от двойника система защиты и блокировок, safety envelope, проверяемый вне оптимизатора.

## Сегментация, зоны и каналы

```
[технологический контур: АСУ ТП, датчики]
              |
      однонаправленный шлюз (только наружу)
              v
[аналитический контур двойника: расчёты, модели, витрины]
              |
      контролируемый канал: заявка -> проверка -> согласование
              v
[контур представления: панели, отчёты, API]
              |
      публикация после проверки агрегационного риска
              v
[открытые сервисы]
```

Ключевой архитектурный принцип: аналитическая часть двойника получает данные из технологического контура, но не имеет обратного пути по умолчанию. Если по сценарию требуется воздействие, обратный канал создаётся как отдельный, узкий, аутентифицированный и журналируемый маршрут с независимой проверкой допустимости команды, а не как «разрешение записи» в существующем соединении.

| Мера | Содержание | Что предотвращает |
|------|------------|-------------------|
| Разделение на зоны | Группировка активов по уровню требований | Распространение компрометации |
| Контроль каналов | Явный перечень разрешённых соединений и протоколов | Нелегитимные потоки |
| Однонаправленная передача | Физическое ограничение направления | Воздействие из аналитического контура на технологический |
| Раздельные среды | Разработка, тест, эксплуатация не соединены | Утечка через тестовые данные и учётные записи |
| Изоляция исследовательского контура | Только обезличенные и синтетические данные | Утечка через эксперименты и обучение |
| Сегментация по данным | Разделение по чувствительности, а не только по сети | Избыточный доступ внутри одной зоны |

## Управление доступом, минимизация и аудит

RBAC задаёт базовое разделение по ролям, ABAC уточняет доступ по контексту: принадлежность объекта к территории или организации пользователя, время, уровень допуска, способ подключения. Практически применяется комбинация: роль определяет набор операций, атрибуты — область видимости.

| Мера | Практическая реализация |
|------|------------------------|
| Минимальные привилегии | Доступ выдаётся под задачу, регулярно пересматривается, автоматически истекает |
| Разделение обязанностей | Разработчик модели не выкладывает её в эксплуатацию самостоятельно |
| Минимизация данных | В контур передаются только необходимые поля, а не таблица целиком |
| Обезличивание и агрегация | Удаление прямых идентификаторов, округление, подавление малых групп |
| Обобщение координат | Понижение точности геопривязки для чувствительных объектов |
| Контроль выгрузок | Лимиты объёма, согласование крупных выгрузок, водяные знаки |
| Аудит | Неизменяемый журнал: кто, когда, какие данные, в каком объёме, по какому основанию |
| Реакция на аномалии доступа | Профилирование поведения, оповещение при нетипичных запросах |

Аудит имеет смысл только при регулярном разборе: журнал, который никто не анализирует, не является мерой защиты. Минимальная практика — периодический отчёт по нетипичным обращениям и обязательный разбор каждого срабатывания.

## Защита моделей и артефактов

| Артефакт | Мера защиты |
|----------|-------------|
| Обучающие наборы | Хранение в контуре происхождения, контроль копирования, обезличивание перед передачей |
| Код подготовки признаков | Версионирование, ревью, контроль целостности |
| Артефакт модели | Реестр с контролем доступа, подпись, проверка целостности при загрузке |
| Конфигурации и параметры | Хранение отдельно от кода, запрет секретов в репозитории |
| Результаты расчётов | Классификация по чувствительности, ограничение экспорта |
| Внешние зависимости | Фиксация версий, проверка на уязвимости, доверенный источник поставки |

Отдельно контролируется происхождение самой модели: если модель обучена в исследовательском контуре, при переносе в продуктивный проверяются не только метрики качества (тема 6), но и то, что в артефакте не сохранились фрагменты чувствительных обучающих данных.

## Комплаенс

| Область | Требование | Практическое следствие |
|---------|------------|------------------------|
| Персональные данные | ФЗ-152 «О персональных данных» и подзаконные акты | Правовое основание обработки, минимизация состава, обезличивание, локализация хранения, регламент реагирования на инциденты |
| Защита информации в государственных системах | Приказы ФСТЭК России, устанавливающие требования к защите информации в информационных системах | Классификация системы, состав организационных и технических мер, аттестация |
| Критическая информационная инфраструктура | Законодательство о безопасности КИИ | Категорирование объектов, требования к средствам защиты и взаимодействию с ГосСОПКА |
| Сведения ограниченного доступа | Законодательство о государственной тайне и служебной информации | Раздельные контуры, запрет выноса, ограничение круга лиц |
| Отраслевые требования | Нормативные акты регуляторов отраслей | Дополнительные ограничения на состав и публикацию данных |
| Международные практики | IEC 62443, NIST SP 800-82, MITRE ATT&CK for ICS | Методическая основа проектирования и оценки защищённости |

Формулировки требований приводятся здесь в общем виде: конкретный состав мер определяется классом системы, категорией объекта и решением уполномоченных органов, поэтому в проекте всегда фиксируется отдельный документ с точными ссылками на действующие редакции нормативных актов.

## Пять контуров проекта и меры защиты

| Контур | Данные | Пользователи | Ключевые меры защиты |
|--------|--------|--------------|----------------------|
| Открытый | Обезличенные и агрегированные сведения | Граждане, бизнес, наука, СМИ | Подавление малых групп, округление и обобщение координат, лимиты API, контроль агрегационного риска, журнал запросов |
| Ведомственный | Детализированные гражданские и ведомственные данные | Федеральные и региональные органы власти | RBAC и ABAC по полномочиям и территории, минимизация состава полей, журнал доступа по ролям, версионирование сценариев |
| Инфраструктурный | Данные о критической и обеспечивающей инфраструктуре | Уполномоченные операторы и регуляторы | Ограничение видимости релевантным участком, запрет экспорта детальных слоёв, журнал каждого просмотра схемы, выдача наружу условий, а не схем |
| Закрытый | Чувствительные сведения ограниченного доступа | Утверждённый узкий круг | Физическая и логическая изоляция, передача поручений без раскрытия основания, строгий контроль круга лиц |
| Исследовательский | Синтетические, тестовые и обезличенные наборы | Наука, разработчики, студенты | Отсутствие первичных чувствительных данных, проверка моделей перед переносом в продуктив, контроль реидентификации |

Правила передачи между контурами (по [Примерам обработки информации для контуров](../../Примеры%20обработки%20информации%20для%20контуров.md)): открытый контур не получает первичные чувствительные данные; ведомственный получает детализацию только в пределах полномочий; инфраструктурный отдаёт наружу ограничения и условия, а не схемы и точки отказа; закрытый передаёт поручения без раскрытия основания; исследовательский отдаёт модели, методики и отчёты о качестве, но не обучающие наборы.

## Чек-лист безопасности перед запуском

- [ ] составлена и утверждена модель угроз с перечнем актуальных нарушителей;
- [ ] активы классифицированы по чувствительности, определена принадлежность каждого контуру;
- [ ] сегментация реализована на уровне сети и на уровне данных, перечень разрешённых каналов зафиксирован;
- [ ] передача из технологического контура однонаправленная, обратный канал (если есть) отдельный, аутентифицированный и журналируемый;
- [ ] роли и права выданы по принципу минимальных привилегий, настроено автоматическое истечение доступа;
- [ ] проверен агрегационный риск для каждой публикуемой связки слоёв, а не только для отдельных слоёв;
- [ ] заданы пороги подавления малых групп и защита от дифференциальных запросов к API;
- [ ] источники телеметрии аутентифицированы, реализована кросс-проверка достоверности;
- [ ] артефакты моделей хранятся в реестре с контролем доступа и проверкой целостности;
- [ ] выкладка модели требует утверждения отдельным лицом, предусмотрен откат к предыдущей версии;
- [ ] аудит включён для доступа, выгрузок, изменений моделей и решений, определён порядок разбора журналов;
- [ ] выполнены требования по персональным данным: основание обработки, минимизация, обезличивание;
- [ ] определён порядок реагирования на инцидент и уведомления уполномоченных органов;
- [ ] проведено тестирование защищённости и устранены выявленные недостатки;
- [ ] персонал ознакомлен с регламентами доступа и порядком действий при инциденте.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Оценка чувствительности по отдельным слоям | Каждый слой сам по себе несекретен | Оценивать риск для совокупности слоёв и связей |
| Разрешение записи в технологический контур «на будущее» | Удобство интеграции | Однонаправленная передача, отдельный канал под конкретный сценарий |
| Обезличивание считается необратимым по умолчанию | Удалены прямые идентификаторы | Проверять риск реидентификации по сочетанию квазиидентификаторов |
| Доступ по должности, а не по задаче | Проще администрировать | RBAC плюс атрибуты, регулярный пересмотр и истечение прав |
| Автоматическое переобучение без утверждения | Стремление к непрерывности | Валидация и ручное утверждение выкладки, контроль источников данных |
| Журналы ведутся, но не анализируются | Формальное выполнение требования | Регламент разбора, оповещения по аномалиям доступа |
| Безопасность добавляется после разработки | Приоритет функциональности | Требования безопасности в постановке задачи и в приёмке |
| Тестовые среды с боевыми данными | Удобство отладки | Синтетические и обезличенные наборы в разработке и тестировании |

## Пример: «Цифровой двойник России»

[Тезисы](../../Тезисы.md) формулируют пять контуров доступа как обязательное архитектурное требование, а не как опцию: без раздельных контуров невозможно одновременно обеспечить открытость и защиту чувствительных сведений. Тезис 6 закрепляет тот же принцип для данных: защита — не надстройка над системой, а её исходное свойство, контуры, ролевой доступ, аудит, обезличивание и обобщение координат заложены с первого дня.

В [Описании](../../Описание.md) в характеристиках системы безопасность раскрыта как «разделение контуров, ролевой доступ, обезличивание, аудит действий, задержка или обобщение чувствительных данных». Здесь перечислены именно те меры, которые в этой теме отнесены к противодействию агрегационному риску: обобщение координат и задержка публикации снижают ценность данных для восстановления режимов работы объектов. В принципах реализации отдельно зафиксировано «не публиковать чувствительные сведения о критической инфраструктуре, логистике и специальных объектах».

Открытый пример из [Примеров обработки информации для контуров](../../Примеры%20обработки%20информации%20для%20контуров.md) содержит конкретную реализацию защиты от инференса: скрытие категорий, в которых менее N работодателей или менее N вакансий, чтобы исключить идентификацию, плюс округление зарплатных вилок до диапазонов и геокодирование только до уровня населённого пункта. Это классическое подавление малых групп. Практическое дополнение, которое студент должен уметь предложить: одного порога недостаточно, если пользователь может строить пересекающиеся срезы — требуется контроль разностных запросов.

Инфраструктурный пример показывает меры контура с наиболее чувствительными данными: подтверждение роли пользователя и причастности к объекту, ограничение видимости релевантным участком сети, журнал каждого просмотра схемы, запрет экспорта детальных слоёв за пределы контура, а наружу — только вывод о допустимости подключения и факт согласования. Это образец правильного разделения: наружу уходит решение, а не данные, на которых оно основано.

## Практическое задание

Разработайте раздел безопасности для сквозного проекта.

1. Составьте модель угроз: объекты защиты, актуальные нарушители, не менее восьми угроз с оценкой вероятности и последствий.
2. Классифицируйте данные проекта по чувствительности и распределите по контурам; для каждого перехода между контурами опишите правило передачи.
3. Спроектируйте сегментацию: зоны, разрешённые каналы, направление передачи, точки контроля.
4. Разработайте матрицу доступа: роли, операции, область видимости по атрибутам.
5. Проведите оценку агрегационного риска для публикуемой части: какие сочетания слоёв дают чувствительный результат и какие меры применяются.
6. Опишите защиту артефактов моделей и порядок их переноса между контурами.
7. Заполните чек-лист безопасности перед запуском с отметками о выполнении и обоснованием исключений.

Критерии приёмки:

- [ ] модель угроз содержит объекты защиты, нарушителей и оценку последствий, а не только перечень мер;
- [ ] для каждого перехода между контурами задано, что именно передаётся и что не передаётся;
- [ ] сегментация описывает направление передачи и точки контроля, а не только список сетей;
- [ ] матрица доступа построена по принципу минимальных привилегий с определённым сроком действия прав;
- [ ] оценка агрегационного риска выполнена для сочетаний слоёв, а не для слоёв по отдельности;
- [ ] предусмотрена защита от дифференциальных запросов и массовых выгрузок через API;
- [ ] описан порядок валидации и утверждения выкладки моделей с возможностью отката;
- [ ] определён состав аудита и регламент разбора журналов;
- [ ] требования по персональным данным и защите информации отражены со ссылками на действующие нормативные акты;
- [ ] чек-лист заполнен полностью, невыполненные пункты имеют письменное обоснование и срок закрытия.

## Проверочные вопросы

1. Почему модель угроз цифрового двойника шире, чем у обычной информационной системы?
2. В чём суть агрегационного риска и почему оценка чувствительности по отдельным слоям недостаточна?
3. Как устроена инференс-атака через разностные запросы и какие меры её ограничивают?
4. Чем отравление данных опаснее для двойника, чем для обычной аналитической системы?
5. Зачем нужна однонаправленная передача из технологического контура и как быть, если требуется воздействие?
6. Чем RBAC отличается от ABAC и почему на практике применяют их сочетание?
7. Какие меры защиты соответствуют инфраструктурному контуру проекта и почему наружу передаётся решение, а не данные?
