# Модуль 4. Тема 2. Выбор платформ и инструментов

> Модуль 4 «Внедрение в компании» · Тема 2 из 2

## Учебные цели

После изучения темы студент сможет:

- различать классы инструментов, из которых собирается цифровой двойник, и определять, какой класс закрывает конкретное требование архитектуры;
- построить весовую матрицу выбора и рассчитать сравнительную оценку вариантов с обоснованием весов;
- принять и защитить решение «купить — собрать — использовать открытый код» для каждого слоя архитектуры;
- оценить риск вендор-лока и снизить его через открытые стандарты и стратегию выхода;
- спроектировать протокол пилотного сравнения инструментов (PoC-протокол) с измеримыми критериями;
- проверить закупочное решение по чек-листу и распознать типовые ошибки выбора.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Платформа цифрового двойника | Среда, объединяющая модель объекта, данные о его состоянии, расчётные сервисы и интерфейсы пользователя |
| IIoT-платформа | Слой подключения промышленного оборудования: сбор телеметрии, управление устройствами, периферийные вычисления |
| Брокер сообщений | Компонент, обеспечивающий асинхронную передачу событий между источниками и потребителями данных |
| Time series DB | Хранилище, оптимизированное под запись и выборку измерений с временной меткой |
| Вендор-лок (vendor lock-in) | Состояние, при котором смена поставщика невозможна или сопоставима по стоимости с новым внедрением |
| Стоимость владения (TCO) | Совокупные затраты за срок жизни: лицензии, инфраструктура, внедрение, поддержка, обучение, выход |
| Открытый стандарт | Публично опубликованная спецификация обмена, реализуемая независимыми поставщиками |
| Asset Administration Shell (AAS) | Стандартизованная цифровая оболочка актива: единая структура описания свойств, документов и сервисов объекта |
| MLOps | Практики и инструменты вывода моделей в эксплуатацию: версионирование, развёртывание, мониторинг, переобучение |
| MDM и каталог данных | Управление мастер-данными и реестр наборов с описанием происхождения, качества и владельца |
| Стратегия выхода (exit strategy) | Заранее описанный порядок переноса данных, моделей и логики к другому поставщику или на собственную инфраструктуру |

## 1. Классы инструментов

Цифровой двойник почти никогда не покупается одним продуктом. Это сборка из одиннадцати классов инструментов, каждый из которых закрывает свой слой архитектуры.

| Класс | Назначение | Что ломается при неверном выборе |
|-------|------------|----------------------------------|
| Платформы цифровых двойников | Связывание модели объекта, состояния и расчётов, управление экземплярами | Платформа диктует модель предметной области, реальный объект в неё не укладывается |
| IIoT-платформы | Подключение оборудования, сбор телеметрии, периферийные вычисления | Часть оборудования не поддерживается, требуется отдельный шлюз на каждый тип |
| Брокеры и потоковая обработка | Транспорт событий, буферизация, обработка потоков в движении | Потеря данных при пиках, невозможность воспроизвести историю событий |
| Хранилища: реляционные, time series, озёра данных | Хранение состояний, измерений, сырых и обработанных наборов | Запросы за длинный период выполняются часами, стоимость хранения растёт нелинейно |
| Среды моделирования и симуляции | Физические, дискретно-событийные, агентные и гибридные модели | Модель невозможно вызвать программно, расчёт остаётся ручной операцией инженера |
| ML-платформы | Обучение и применение статистических и обучаемых моделей | Модель работает у аналитика на ноутбуке и нигде больше |
| ГИС и 3D-визуализация | Пространственная привязка, отображение геометрии и территории | Визуализация не масштабируется на реальный объём объектов |
| BI-инструменты | Отчётность, дашборды, самообслуживание пользователей | Появляется параллельная версия правды, расходящаяся с двойником |
| Средства интеграции (ETL/ELT, шины, коннекторы) | Извлечение и согласование данных из систем-источников | Каждый новый источник требует уникальной разработки |
| MDM и каталоги данных | Единые справочники, происхождение, качество, владельцы наборов | Один объект существует под тремя идентификаторами, агрегаты не сходятся |
| MLOps | Версионирование, развёртывание, мониторинг деградации моделей | Никто не замечает, что модель перестала быть точной полгода назад |
| Информационная безопасность | Управление доступом, сегментация, аудит, защита моделей и данных | Требования ИБ вводятся после архитектуры и ломают её |

Практическое правило: выбор начинается не с платформы, а с матрицы требований и перечня источников данных. Класс инструмента определяется требованием, а не наоборот.

## 2. Критерии выбора и весовая матрица

Девять критериев покрывают технический, экономический и организационный аспекты выбора.

| Критерий | Вес | Что оценивается |
|----------|-----|-----------------|
| Функциональность | 0,18 | Покрытие требований матрицы требований без доработок |
| Интеграция и открытость стандартов | 0,15 | Поддержка OPC UA, MQTT, AAS, OGC, REST; наличие документированного API |
| Масштабируемость | 0,12 | Поведение при росте числа объектов, частоты данных и пользователей |
| Стоимость владения (TCO) | 0,15 | Лицензии, инфраструктура, внедрение, поддержка, обучение, выход за 5 лет |
| Зрелость и поддержка | 0,10 | Срок на рынке, число внедрений, качество документации, SLA поддержки |
| Компетенции команды | 0,10 | Наличие или доступность специалистов, стоимость обучения |
| Требования ИБ и локализация | 0,08 | Соответствие политике безопасности, размещение данных, сертификация |
| Реестр отечественного ПО | 0,07 | Наличие в едином реестре российского ПО, если это обязательное требование заказчика |
| Вендор-лок и стратегия выхода | 0,05 | Возможность выгрузить данные и модели в открытых форматах, стоимость миграции |

Веса не универсальны: для государственного заказчика вес критериев локализации и реестра может вырасти до 0,25 суммарно, для исследовательского контура — упасть до нуля. Веса согласовываются до просмотра вариантов, иначе они подгоняются под заранее выбранного поставщика.

### Пример расчёта: три гипотетических варианта

Оценка по шкале 1–5. Варианты условные и служат для отработки метода, а не для рекомендации конкретных продуктов.

| Критерий | Вес | Вариант А: зарубежная коммерческая платформа | Вариант Б: отечественная платформа из реестра | Вариант В: сборка на открытом коде |
|----------|-----|----------------------------------------------|-----------------------------------------------|------------------------------------|
| Функциональность | 0,18 | 5 | 3 | 3 |
| Интеграция и стандарты | 0,15 | 4 | 4 | 5 |
| Масштабируемость | 0,12 | 5 | 3 | 4 |
| Стоимость владения | 0,15 | 2 | 3 | 4 |
| Зрелость и поддержка | 0,10 | 5 | 3 | 2 |
| Компетенции команды | 0,10 | 3 | 3 | 2 |
| Требования ИБ и локализация | 0,08 | 1 | 5 | 4 |
| Реестр отечественного ПО | 0,07 | 1 | 5 | 2 |
| Вендор-лок и выход | 0,05 | 1 | 3 | 5 |
| **Взвешенная сумма** | **1,00** | **3,40** | **3,45** | **3,48** |

Расчёт варианта А: 5×0,18 + 4×0,15 + 5×0,12 + 2×0,15 + 5×0,10 + 3×0,10 + 1×0,08 + 1×0,07 + 1×0,05 = 0,90 + 0,60 + 0,60 + 0,30 + 0,50 + 0,30 + 0,08 + 0,07 + 0,05 = **3,40**.

Расчёт варианта Б: 0,54 + 0,60 + 0,36 + 0,45 + 0,30 + 0,30 + 0,40 + 0,35 + 0,15 = **3,45**.

Расчёт варианта В: 0,54 + 0,75 + 0,48 + 0,60 + 0,20 + 0,20 + 0,32 + 0,14 + 0,25 = **3,48**.

Выводы, которые следует извлечь из примера:

1. **Разрыв в 0,08 балла не является основанием для выбора.** Все три варианта уложились в интервал менее 3%: при такой разнице решение принимается по стоп-факторам и результатам PoC, а не по арифметике. Матрица здесь работает не как механизм выбора, а как способ увидеть, что варианты сопоставимы и спор идёт не о баллах.
2. **Стоп-факторы важнее суммы.** Если заказчик обязан закупать ПО из реестра, вариант А выбывает независимо от набранных баллов и от того, что по функциональности он лучший. Стоп-факторы проверяются до расчёта, а не взвешиваются вместе с остальными критериями.
3. **Веса — предмет протокола.** Изменение веса локализации с 0,08 до 0,20 меняет победителя. Поэтому веса фиксируются письменно и подписываются до сбора оценок.
4. **Низкие оценки компетенций у варианта В — реальная стоимость.** Открытый код бесплатен по лицензии и дорог по людям.

## 3. «Купить — собрать — открытый код»

| Аспект | Купить (коммерческий продукт) | Собрать самим | Открытый код |
|--------|-------------------------------|---------------|--------------|
| Скорость первого результата | Высокая | Низкая | Средняя |
| Стоимость на старте | Высокая (лицензии) | Средняя (люди) | Низкая |
| Стоимость на горизонте 5 лет | Растёт с числом объектов и пользователей | Стабильная, но требует постоянной команды | Средняя, смещена в оплату труда |
| Соответствие специфике объекта | Ограничено моделью вендора | Полное | Высокое при наличии компетенций |
| Зависимость от внешней стороны | Высокая | Отсутствует | Средняя (сообщество, форки) |
| Риск при уходе поставщика с рынка | Критический | Отсутствует | Управляемый (код остаётся) |
| Требуемые компетенции | Настройка и эксплуатация | Полный цикл разработки | Разработка и сопровождение стека |
| Поддержка и ответственность | Договор, SLA | Внутренняя | Через интегратора или своими силами |
| Где уместно | Типовые задачи, стандартные объекты | Уникальное конкурентное преимущество | Инфраструктурные слои: транспорт, хранение, обработка |

Практический подход — гибридный: инфраструктурные слои (брокер, хранилище, каталог) собираются на открытом коде и стандартах, предметная модель и логика принятия решений разрабатываются внутри как источник преимущества, а специализированные расчётные среды приобретаются, поскольку их воспроизведение экономически бессмысленно.

Отдельно: решение «собрать самим» требует честного ответа на вопрос, кто будет сопровождать результат через три года. Если ответ «тот же один разработчик» — это не собственная разработка, а персональная зависимость.

## 4. Открытые стандарты как защита от вендор-лока

| Стандарт | Область | Что даёт при внедрении |
|----------|---------|------------------------|
| OPC UA | Промышленная связь, информационное моделирование оборудования | Единый способ читать данные разнородного оборудования и описывать его семантику |
| MQTT и спецификация Sparkplug | Лёгкий обмен сообщениями «издатель — подписчик» | Транспорт телеметрии при нестабильных каналах; Sparkplug задаёт единый формат полезной нагрузки и состояния устройств |
| Asset Administration Shell (AAS) | Цифровая оболочка актива | Стандартизованное описание свойств и документов объекта, переносимое между системами |
| Стандарты OGC | Геопространственные сервисы и форматы | Обмен пространственными слоями между ГИС разных поставщиков |
| ISO 23247 | Референсная архитектура цифрового двойника для производства | Общий язык описания компонентов и границ решения при обсуждении с поставщиками |
| ISO/IEC 30173 | Терминология и концептуальная структура | Единое понимание терминов в техническом задании и договоре |
| IEC 62443 | Безопасность промышленных систем автоматизации | Проверяемые требования ИБ, включаемые в закупочную документацию |

Как стандарты работают против вендор-лока на практике:

1. **Требование в договоре.** Поддержка стандарта указывается как обязательное требование с проверкой на приёмке, а не как маркетинговое заявление вендора.
2. **Проверка реализации.** «Поддержка OPC UA» бывает частичной. На PoC проверяется конкретный сценарий: чтение нужных узлов, подписка на изменения, безопасное соединение.
3. **Право на выгрузку.** В договоре фиксируется право выгрузить все данные и конфигурации в документированном формате в любой момент и после расторжения.
4. **Граница проприетарного слоя.** Проприетарный компонент допустим, если он изолирован и заменяем; недопустим, если через него проходят все данные.

## 5. Импортозамещение и реестр российского ПО

Для государственных заказчиков и части компаний с государственным участием применение программного обеспечения из единого реестра российских программ является закупочным требованием. Практические следствия для проекта внедрения:

| Вопрос | Что нужно сделать |
|--------|-------------------|
| Обязателен ли реестр для вашего заказчика | Уточнить статус заказчика и категорию системы до формирования короткого списка |
| Есть ли в реестре решения нужного класса | Проверить по классификатору реестра, зафиксировать перечень с датой проверки |
| Что делать при отсутствии класса в реестре | Оформить обоснование, рассмотреть сборку на открытом коде с последующей регистрацией собственного решения |
| Как соотносятся реестр и открытый код | Решение на открытом коде может быть зарегистрировано в реестре как самостоятельный продукт при выполнении условий регистрации |
| Как избежать формального подхода | Проверять функциональное соответствие требованиям на PoC, а не ограничиваться фактом наличия в реестре |

Корректная позиция при обучении и в проектной документации — нейтральная: фиксируется процедура проверки и источник (официальный реестр), а не оценочные суждения о конкретных продуктах. Характеристики решений подтверждаются документацией поставщика и результатами собственного пилотного сравнения, а не рекламными материалами и не отраслевыми рейтингами.

Проект «Цифровой двойник России» формулирует это как сквозной принцип: на каждом этапе технологические зависимости проверяются на возможность импортозамещения, а приоритет отдаётся отечественному стеку, локальному хранению и переносимости компонентов.

## 6. Пилотное сравнение инструментов: PoC-протокол

Выбор по документации и презентациям поставщика недостоверен. Финалистов короткого списка сравнивают на одинаковой задаче по единому протоколу.

| Раздел протокола | Содержание |
|------------------|------------|
| Цель | Проверяемая гипотеза: например, «инструмент подключает наш тип контроллеров по OPC UA и удерживает поток 5000 тегов в секунду» |
| Срок | 2–4 недели на каждый вариант, одинаковый для всех участников |
| Тестовые данные | Один и тот же набор: 12 месяцев истории и сутки потока с реального объекта, включая известные аномалии и пропуски |
| Сценарии | 3–5 сценариев, повторяющих реальные задачи пользователя, а не демонстрационные примеры вендора |
| Критерии | Измеримые: срок подключения источника, задержка обработки, точность расчёта, число строк собственного кода, время обучения пользователя |
| Кто оценивает | Дата-инженер (интеграция), специалист по моделированию (расчёты), ИБ (соответствие), владелец процесса (полезность), эксплуатация (сопровождаемость) |
| Условия равенства | Одинаковый объём поддержки от поставщика, одинаковая инфраструктура, одинаковый доступ к документации |
| Форма результата | Заполненная таблица оценок, журнал возникших проблем, письменное особое мнение каждого оценивающего |
| Решение | Взвешенная оценка + результат PoC + стоп-факторы; протокол подписывается всеми участниками |

Обязательное правило: критерии и веса фиксируются до начала PoC. Критерии, сформулированные после демонстрации, всегда описывают сильные стороны того варианта, который понравился.

## 7. Чек-лист выбора инструмента

- [ ] Составлена матрица требований, каждое требование связано с классом инструмента
- [ ] Определены стоп-факторы (ИБ, локализация, реестр, бюджет) и применены до расчёта баллов
- [ ] Веса критериев согласованы и подписаны до просмотра вариантов
- [ ] Короткий список содержит не менее трёх вариантов, включая вариант на открытом коде
- [ ] Для каждого варианта рассчитан TCO на 5 лет, а не цена лицензии
- [ ] Проведён PoC на собственных данных по единому протоколу для всех финалистов
- [ ] Проверена фактическая, а не заявленная поддержка открытых стандартов
- [ ] Оценены компетенции команды и стоимость обучения по каждому варианту
- [ ] Зафиксировано право выгрузки данных, моделей и конфигураций в документированных форматах
- [ ] Описана стратегия выхода: что переносим, куда, за какой срок, какой ценой
- [ ] Требования ИБ включены в договор и проверяются на приёмке
- [ ] Решение оформлено протоколом с расчётом, особыми мнениями и подписями участников

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Выбор платформы до формулировки требований | Давление сроков, доступность красивой презентации | Сначала матрица требований и перечень источников, потом короткий список |
| Оценка по демонстрации вендора | Демонстрация идёт на подготовленных данных | PoC на собственных данных с известными дефектами |
| Игнорирование стоимости владения | В расчёт берётся только цена лицензии первого года | Расчёт TCO на 5 лет с учётом внедрения, поддержки, обучения и выхода |
| Веса критериев подбираются после просмотра вариантов | Желание обосновать уже принятое решение | Фиксация и подписание весов до сбора оценок |
| Покупка «всё в одном» | Кажется, что один поставщик проще | Проверить, какие слои реально закрыты, а какие требуют доработки |
| Пренебрежение компетенциями | Считается, что обучить можно кого угодно | Оценка сроков и стоимости обучения как отдельная строка бюджета |
| Подключение ИБ на приёмке | ИБ воспринимается как согласующая, а не проектирующая сторона | Требования ИБ включаются в закупочную документацию с самого начала |
| Отсутствие стратегии выхода | Обсуждать расставание на этапе покупки психологически неудобно | Порядок и сроки выгрузки данных и моделей фиксируются в договоре |
| Формальная проверка реестра | Требование закрывается справкой без проверки функциональности | Функциональная проверка на PoC независимо от статуса в реестре |
| Проприетарные форматы хранения | Не проверяется, в чём именно хранятся данные и модели | Требование хранения в документированных форматах с возможностью выгрузки |

## Пример: «Цифровой двойник России»

Проект даёт пример технологического выбора в условиях жёстких ограничений по суверенитету и безопасности.

| Аспект выбора | Позиция проекта |
|---------------|-----------------|
| Проблема, порождающая требование | [Проблемы и задачи](../../Проблемы%20и%20задачи.md) фиксируют зависимость геоаналитики и моделирования от зарубежных платформ как риск устойчивости |
| Приоритет стека | Отечественный стек, локальное хранение, контролируемый обмен ([Описание](../../Описание.md)) |
| Переносимость | Технологическая независимость обеспечивается через открытые стандарты и переносимость компонентов, а не только через выбор поставщика |
| Интеграция вместо замены | Существующие системы (НСПД, ЕМИСС, ГИСП, ФГИС ЕФГИ) подключаются как источники, что делает качество коннекторов и средств интеграции критическим классом инструментов |
| Единые справочники | Приведение к классификаторам ОКВЭД, ОКТМО, ФИАС — типичная задача MDM-слоя, вынесенная в основание архитектуры ([Бизнес-план](../../Бизнес-план.md)) |
| Требования к хранилищу | [MVP](../../MVP.md) требует загрузки GeoJSON, CSV, API и табличных выгрузок с хранением источника, даты обновления, лицензии, качества и владельца — это требование к каталогу данных, а не к карте |
| Безопасность как класс инструментов | Пять контуров доступа, ролевая модель, журналирование и обезличивание проектируются как отдельный слой, а не настраиваются поверх готового решения |
| Регистрация продукта | В структуре расходов отдельной строкой заложены юридические расходы и регистрация в реестре ПО |

Показательно, что проект нигде не начинает с выбора платформы. Сначала формулируются контуры доступа, перечень источников, правила межконтурного обмена и требования к прослеживаемости данных, и только затем обсуждается технологическая реализация. Это ровно та последовательность, которую описывает раздел 1 настоящей темы.

## Практическое задание

**Задание 4.2.** Для объекта вашего сквозного проекта подготовьте обоснование выбора технологического стека.

Состав работы:

1. Составьте таблицу «требование → класс инструмента» для 10–15 требований из матрицы требований вашего проекта.
2. Для двух наиболее критичных классов сформируйте короткий список из трёх вариантов, включая вариант на открытом коде.
3. Согласуйте и обоснуйте веса девяти критериев применительно к вашему заказчику; объясните, почему веса отличаются от приведённых в теме.
4. Заполните весовую матрицу и приведите арифметический расчёт взвешенной суммы для каждого варианта.
5. Отдельно перечислите стоп-факторы и покажите, какие варианты они исключают независимо от баллов.
6. Для каждого слоя архитектуры примите решение «купить — собрать — открытый код» с обоснованием по таблице раздела 3.
7. Составьте PoC-протокол сравнения финалистов по всем девяти разделам таблицы раздела 6.
8. Опишите стратегию выхода: перечень выгружаемых артефактов, форматы, сроки, оценка стоимости миграции.

Критерии приёмки:

- [ ] Каждое требование сопоставлено с классом инструмента, ни один класс не введён без требования
- [ ] Веса критериев обоснованы характеристиками заказчика и зафиксированы до сравнения вариантов
- [ ] Сумма весов равна единице, расчёт взвешенной суммы приведён полностью и проверяем вручную
- [ ] Стоп-факторы перечислены отдельно и применены до расчёта баллов
- [ ] В коротком списке присутствует вариант на открытом коде и оценена стоимость компетенций для него
- [ ] Расчёт стоимости владения выполнен на 5 лет и включает внедрение, поддержку, обучение и выход
- [ ] Для каждого слоя решение «купить — собрать — открытый код» обосновано, а не выбрано по умолчанию
- [ ] PoC-протокол содержит измеримые критерии, тестовые данные с известными дефектами и состав оценивающих
- [ ] Указаны конкретные открытые стандарты, поддержка которых проверяется на приёмке
- [ ] Стратегия выхода описывает форматы выгрузки и оценку стоимости миграции в человеко-месяцах
- [ ] Характеристики продуктов подтверждены документацией или собственной проверкой, без ссылок на рекламные материалы
