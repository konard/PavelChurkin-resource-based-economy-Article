# Модуль 2. Тема 3. Интеграция и транспорт — OPC UA, MQTT, REST, потоковые данные и синхронизация

> Модуль 2 «Архитектура и данные» · Тема 3 из 6

## Учебные цели

После изучения темы студент сможет:

- сравнивать протоколы интеграции по модели взаимодействия, задержке, надёжности и безопасности и обоснованно выбирать один из них;
- проектировать топики MQTT и адресное пространство OPC UA для промышленного объекта;
- определять частоту синхронизации исходя из постоянной времени объекта и цели сценария;
- обеспечивать идемпотентность, дедупликацию и корректную работу с метками времени;
- проектировать защищённый периметр интеграции: DMZ, однонаправленные шлюзы, шифрование, аутентификация.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| OPC UA | Открытая платформонезависимая архитектура промышленной интеграции с встроенной информационной моделью и защитой |
| MQTT | Лёгкий протокол обмена сообщениями по модели «издатель — подписчик» через брокер |
| QoS | Уровень гарантии доставки сообщения: 0 — не более одного раза, 1 — не менее одного раза, 2 — ровно один раз |
| Sparkplug B | Спецификация поверх MQTT, задающая структуру топиков, полезной нагрузки и управление состоянием устройств |
| CDC | Захват изменений данных из журнала транзакций базы-источника |
| Backpressure | Механизм замедления производителя, когда потребитель не успевает обрабатывать поток |
| Идемпотентность | Свойство операции давать один и тот же результат при повторном применении |
| Event time / ingestion time | Время наступления события у источника и время его поступления в платформу |
| Data diode | Аппаратный однонаправленный шлюз, физически исключающий обратную передачу |
| Постоянная времени объекта | Характерное время, за которое объект существенно меняет состояние |

## 1. Сравнение протоколов

| Протокол | Модель | Типовая задержка | Надёжность | Безопасность | Где применять |
|----------|--------|------------------|------------|--------------|---------------|
| OPC UA Client/Server | Запрос-ответ и подписки | 10–500 мс | Подтверждения, восстановление подписки | Встроенная: сертификаты, подпись, шифрование | Связь с АСУ ТП, чтение тегов, семантическая модель оборудования |
| OPC UA PubSub | Издатель-подписчик поверх UDP/MQTT | 1–50 мс | Зависит от транспорта | Наследует профили безопасности OPC UA | Множественная рассылка телеметрии, низкие задержки |
| MQTT | Издатель-подписчик через брокер | 10–200 мс | QoS 0/1/2, сессии, retained | TLS, аутентификация клиента, ACL на топики | Телеметрия с распределённых узлов, нестабильные каналы |
| REST/HTTP | Запрос-ответ | 50 мс — секунды | Повторы на стороне клиента | TLS, токены, OAuth 2.0 | Справочники, реестры, публикация результатов, интеграция систем |
| gRPC | RPC поверх HTTP/2, потоки | 5–50 мс | Потоковая передача, дедлайны | TLS, mTLS | Межсервисное взаимодействие внутри платформы |
| Файловая выгрузка (CSV) | Пакетная передача | Часы — сутки | Контрольные суммы, манифест | Защита канала и хранилища | Открытые данные, ведомственные реестры, первичная загрузка |
| Kafka | Распределённый журнал | 5–100 мс | Репликация, хранение с повтором чтения | TLS, SASL, ACL | Буфер между источниками и потребителями, потоковая обработка |
| CDC | Чтение журнала транзакций | Секунды | Гарантия порядка в рамках таблицы | Права на репликацию | Синхронизация с ERP/MES без нагрузки на исходную БД |

Ключевой принцип выбора: **протокол определяется не модой, а сочетанием требуемой задержки, надёжности канала и того, кто инициирует обмен**. Если источник за NAT и связь нестабильна — издатель-подписчик. Если нужен семантический доступ к структуре оборудования — OPC UA. Если данные обновляются раз в квартал — CSV, и не нужно строить брокер.

## 2. OPC UA: информационная модель

Главная ценность OPC UA не в транспорте, а в том, что данные приходят вместе со структурой и типами. Вместо плоского списка тегов клиент видит дерево объектов с описанными связями.

```
Objects
└── Насосная станция №3            (ObjectType: PumpStation)
    ├── Насос П-101                 (ObjectType: Pump)
    │   ├── Переменные
    │   │   ├── Давление на выходе  (Double, EngineeringUnits: bar)
    │   │   ├── Расход              (Double, EngineeringUnits: m3/h)
    │   │   ├── Ток двигателя       (Double, EngineeringUnits: A)
    │   │   └── Состояние           (Enum: Остановлен/Работа/Авария)
    │   ├── Методы
    │   │   └── Запросить самодиагностику()
    │   └── События
    │       └── Превышение вибрации (AlarmConditionType)
    └── Насос П-102                 (ObjectType: Pump)
```

Практические следствия:

- один тип `Pump` описывается один раз и переиспользуется для всех насосов — модель двойника не переписывается при добавлении оборудования;
- единицы измерения передаются вместе со значением, что снимает целый класс ошибок;
- подписка (`Subscription` с `MonitoredItems`) передаёт только изменения с заданным деадбендом, снижая трафик;
- каждое значение сопровождается меткой времени источника и кодом качества `StatusCode` — это готовый вход для проверок из [Темы 2](Тема%202.%20Источники%20данных%20—%20датчики,%20IIoT,%20SCADA,%20MES,%20ERP,%20журналы%20событий.md).

## 3. MQTT: топики, QoS, retained

Структура топиков — это архитектурное решение, а не техническая мелочь. Плохая схема топиков делает невозможной подписку по маске и вынуждает потребителей парсить строки.

```
<организация>/<площадка>/<установка>/<устройство>/<тип>/<метрика>

dt/perm/station-3/pump-101/telemetry/pressure_out
dt/perm/station-3/pump-101/telemetry/flow
dt/perm/station-3/pump-101/state
dt/perm/station-3/pump-101/event/alarm
dt/perm/station-3/pump-101/cmd/setpoint     ← нисходящий поток
```

Правила проектирования топиков:

- от общего к частному, чтобы работали подписки вида `dt/perm/station-3/+/telemetry/#`;
- идентификаторы устройств — стабильные, не зависящие от места монтажа;
- команды в отдельной ветке `cmd/`, чтобы разграничить права на публикацию через ACL;
- никаких пробелов, кириллицы и изменяемых атрибутов в имени топика.

| Уровень QoS | Гарантия | Стоимость | Когда применять |
|-------------|----------|-----------|-----------------|
| 0 | Не более одного раза, потери возможны | Минимальная | Частая телеметрия, где потеря отсчёта некритична |
| 1 | Не менее одного раза, дубликаты возможны | Средняя | Большинство событий; требует дедупликации на приёме |
| 2 | Ровно один раз | Высокая | Команды, финансовые и юридически значимые события |

Дополнительно: **retained**-сообщение хранит последнее значение в топике, и новый подписчик сразу получает текущее состояние — удобно для статусов, вредно для потока измерений. **Last Will and Testament** позволяет брокеру объявить об отключении узла, что даёт достоверный признак «связь потеряна» вместо молчаливого отсутствия данных. Спецификация **Sparkplug B** стандартизирует именно эти механизмы: структуру топиков, состояние `birth`/`death` устройств и типизированную полезную нагрузку.

Пример полезной нагрузки:

```json
{
  "device_id": "pump-101",
  "event_time": "2026-07-19T08:41:12.480Z",
  "ingestion_time": "2026-07-19T08:41:12.930Z",
  "seq": 84213,
  "quality": "good",
  "metrics": {
    "pressure_out": { "value": 6.42, "unit": "bar" },
    "flow":         { "value": 118.7, "unit": "m3/h" },
    "current":      { "value": 41.2, "unit": "A" }
  }
}
```

Поля `seq` и `event_time` обязательны: первое даёт дедупликацию, второе — корректный порядок обработки.

## 4. Частота синхронизации

Частота обмена выбирается по постоянной времени объекта и цели сценария, а не по максимуму возможностей оборудования. Избыточная частота — это стоимость хранения и трафика без прироста ценности.

Практическое правило: период опроса должен быть в 5–10 раз меньше постоянной времени процесса, который требуется различать. Для задач обнаружения дефектов по вибрации действует теорема Котельникова: частота дискретизации не менее удвоенной верхней частоты интересующего спектра.

| Сценарий | Постоянная времени объекта | Частота синхронизации | Допустимая задержка |
|----------|----------------------------|-----------------------|---------------------|
| Диагностика подшипника по вибрации | Миллисекунды | 5–20 кГц (окнами) | Минуты (передаются признаки, не сырой сигнал) |
| Защита насосного агрегата | Секунды | 10–100 Гц | 100 мс |
| Контроль технологического режима | Минуты | 1 Гц | 5 с |
| Тепловой режим здания | Часы | 1 раз в 5 минут | 10 минут |
| Плановая выработка участка | Смена | 1 раз в смену | 1 час |
| Загрузка транспортного узла | Сутки | 1 раз в час | 1 час |
| Кадровый дефицит региона | Месяцы | 1 раз в сутки | 24 часа |
| Ресурсный паспорт территории | Годы | 1 раз в квартал | 1 месяц |

## 5. Надёжность обмена: буферизация, backpressure, идемпотентность

| Проблема | Проявление | Решение |
|----------|------------|---------|
| Обрыв канала | Данные теряются, пока связь недоступна | Локальный буфер на edge с ограниченной глубиной и дозаписью после восстановления |
| Потребитель не успевает | Растёт очередь, память исчерпывается | Backpressure: замедление производителя, отбрасывание по политике, буфер на диске |
| Повторная доставка | Дубликаты записей, задвоенные показатели | Идемпотентная запись по ключу `(device_id, seq)` или `(object, event_time, metric)` |
| Нарушенный порядок | Поздние сообщения ломают агрегаты | Обработка по event time с окном допустимого опоздания и пересчётом |
| Расхождение часов | Ряд «прыгает» во времени, события переставлены | Синхронизация NTP/PTP, хранение UTC, фиксация смещения источника |
| Всплеск нагрузки | Пиковый поток перегружает хранилище | Брокер как амортизатор между приёмом и записью |

Пример идемпотентной вставки:

```sql
INSERT INTO raw.measurements (device_id, metric, event_time, value, seq, quality)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (device_id, metric, event_time) DO NOTHING;
```

Отдельно о времени: в системе должны храниться **обе** метки — `event_time` (когда произошло у источника) и `ingestion_time` (когда получено платформой). Разница между ними — прямая метрика своевременности и первый индикатор деградации канала. Все метки хранятся в UTC; локальный часовой пояс — атрибут отображения, а не хранения.

## 6. Безопасность транспорта и периметр

| Уровень защиты | Механизм | Комментарий |
|----------------|----------|-------------|
| Канал | TLS для MQTT, HTTPS для REST, профили безопасности OPC UA | Шифрование обязательно и внутри периметра |
| Стороны обмена | Сертификаты, mTLS, токены с коротким сроком | Учётная запись на устройство, а не общая на парк |
| Права | ACL на топики и узлы адресного пространства | Право публикации в `cmd/` — только у управляющего сервиса |
| Сегментация | Промышленная DMZ между АСУ ТП и корпоративной сетью | Прямые подключения из офисной сети в контур АСУ ТП запрещены |
| Однонаправленность | Data diode, однонаправленный шлюз | Применяется, когда обратный поток недопустим в принципе |
| Наблюдаемость | Журналы подключений, аномалии трафика, аудит команд | Каждая команда фиксируется с автором и основанием |

Архитектурное следствие: если объект относится к критической инфраструктуре, интеграция проектируется как **экспорт наружу**, а не как доступ внутрь. Двойник получает срез состояния через шлюз, а управляющие воздействия остаются в контуре оператора.

```
[Контур АСУ ТП] --OPC UA--> [Шлюз в промышленной DMZ] ==диод==> [Платформа двойника]
       ▲                                                                │
       └──────────── решения оператора (вне канала передачи) ◄──────────┘
```

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Опрос с максимально возможной частотой | «Пусть будет, вдруг пригодится» | Частота от постоянной времени объекта и цели сценария |
| Единственная метка времени | Кажется, что достаточно одной | Хранить event time и ingestion time раздельно |
| QoS 2 для всей телеметрии | Стремление к «максимальной надёжности» | QoS по классу сообщения; дедупликация вместо QoS 2 |
| Топики с изменяемыми атрибутами в имени | Удобно на старте | Стабильные идентификаторы, атрибуты — в полезной нагрузке |
| Отсутствие буфера на edge | Канал считается надёжным | Локальный буфер с политикой переполнения |
| Прямое подключение из корпоративной сети в АСУ ТП | Экономия на шлюзе | Промышленная DMZ, при необходимости однонаправленный шлюз |
| Неидемпотентная загрузка | Повторы не предусмотрены | Ключ дедупликации и `ON CONFLICT DO NOTHING` |
| Брокер вместо файловой загрузки для квартальных данных | Стремление к единой технологии | Простой ETL там, где данные меняются редко |

## Пример: «Цифровой двойник России»

Для федеральной платформы транспорт устроен иначе, чем на производственном объекте: доминируют не OPC UA и MQTT, а файловые выгрузки и REST API. Документ [Источники CSV и API.md](../../Источники%20CSV%20и%20API.md) прямо фиксирует очередность: сначала CSV/XLSX по прямой ссылке, затем REST API с JSON, затем геодампы. Обоснование инженерное: файл не требует ключей, согласований и обработки лимитов, поэтому рабочая база собирается за недели без единого согласования.

Формула обновления базы из того же документа:

```
[Источник CSV] --(Airflow DAG по расписанию)--> [Загрузка файла]
   --> [Нормализация + паспорт качества] --> [PostGIS / объектное хранилище]
   --> [Каталог метаданных: source_version = дата выгрузки]
```

Соответствие частот сценариям видно по каталогу источников: климатические ряды Росгидромета — месяц, реестры ЧС — квартал, вакансии «Работы России» — сутки, очаги пожаров NASA FIRMS — 1–4 раза в сутки, дампы OpenStreetMap от Geofabrik обновляются ежесуточно, но берутся раз в месяц. Последний случай — образцовая иллюстрация правила: частота загрузки определяется потребностью сценария, а не частотой публикации источника.

Промышленный транспорт появляется в проекте на уровне сценария «цифровой двойник предприятия или отраслевого кластера» из [Описания](../../Описание.md), когда производственные объекты подключаются к региональной модели. Здесь и возникают OPC UA и MQTT — но с обязательной оговоркой безопасности: чувствительные данные критической инфраструктуры передаются только в виде условий и ограничений, без сетевых схем, что архитектурно означает однонаправленный экспорт агрегатов через шлюз.

## Практическое задание

Спроектируйте транспортный слой для вашего сквозного проекта.

1. Для каждого источника из каталога Темы 2 выберите протокол и обоснуйте выбор тремя критериями.
2. Спроектируйте схему топиков MQTT (или адресное пространство OPC UA) не менее чем для 3 устройств и 8 метрик.
3. Составьте таблицу «сценарий → постоянная времени объекта → частота синхронизации → допустимая задержка» на 5 строк.
4. Опишите механизм дедупликации: ключ, место применения, поведение при повторе.
5. Опишите поведение при обрыве канала на 6 часов: глубина буфера, политика переполнения, порядок дозаписи.
6. Нарисуйте схему периметра безопасности с указанием сегментов и точек контроля.

Критерии приёмки:

- [ ] Выбор протокола для каждого источника обоснован задержкой, надёжностью канала и инициатором обмена
- [ ] Схема топиков допускает подписку по маске и не содержит изменяемых атрибутов
- [ ] Уровень QoS назначен по классу сообщения, а не единый для всего потока
- [ ] Для каждого сценария частота выведена из постоянной времени объекта
- [ ] Указан ключ дедупликации и приведён пример идемпотентной записи
- [ ] Описано хранение event time и ingestion time в UTC
- [ ] Схема периметра содержит сегментацию и правило для команд нисходящего потока
