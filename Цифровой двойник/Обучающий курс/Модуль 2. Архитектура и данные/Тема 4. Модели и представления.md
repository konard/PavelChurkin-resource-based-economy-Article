# Модуль 2. Тема 4. Модели и представления

> Модуль 2 «Архитектура и данные» · Тема 4 из 6

## Учебные цели

После изучения темы студент сможет:

- различать классы моделей цифрового двойника и подбирать класс под задачу и доступные данные;
- оценивать компромисс между точностью, вычислительной стоимостью и требуемыми входными данными;
- строить композицию из нескольких моделей и организовывать co-simulation;
- версионировать модели совместно с данными и оформлять карточку модели;
- проектировать представления результатов под конкретные роли пользователей.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Геометрическая модель | Описание формы и пространственного положения объекта: CAD, BIM, 3D-сетка, ГИС-слой |
| Физико-математическая модель | Описание процесса уравнениями сохранения и состояния, решаемыми численно |
| ROM | Редуцированная модель — упрощение полной физической модели с сохранением ключевого поведения при кратно меньшей стоимости расчёта |
| Суррогатная модель | Аппроксимация отклика сложной модели, обученная на её же расчётах |
| Дискретно-событийная модель | Модель, в которой состояние меняется в моменты наступления событий |
| Агентная модель | Модель, где поведение системы возникает из взаимодействия автономных агентов |
| Графовая модель | Представление объектов и их связей в виде вершин и рёбер |
| Онтология | Формальное описание понятий предметной области и отношений между ними |
| AAS | Asset Administration Shell — стандартизованная цифровая оболочка актива с набором субмоделей |
| Карточка модели | Документ с назначением, допущениями, входами, метриками качества и границами применимости модели |

## 1. Классы моделей

| Тип модели | Входные данные | Вычислительная стоимость | Точность | Применимость |
|------------|----------------|--------------------------|----------|--------------|
| Геометрическая (CAD/BIM/3D) | Чертежи, обмеры, лазерное сканирование | Низкая при отображении, высокая при подготовке | Геометрическая точность до миллиметров | Визуализация, коллизии, планировка, объёмы |
| ГИС / геопространственная | Координаты, слои, рельеф, границы | Низкая — средняя | Зависит от точности координат | Территориальный анализ, доступность, маршруты |
| Физико-математическая (ОДУ) | Параметры объекта, начальные условия, воздействия | Средняя | Высокая в рамках допущений | Динамика агрегатов, тепловые и гидравлические режимы |
| Полевая (FEM/CFD, ДУЧП) | Геометрия, сетка, свойства среды, граничные условия | Очень высокая (часы — сутки) | Наивысшая при корректной постановке | Прочность, поток, нагрев, проектные расчёты |
| ROM / суррогатная | Выборка расчётов полной модели | Низкая после обучения | Ниже исходной, приемлемая в обученной области | Реальновременные сценарии, оптимизация, what-if |
| Дискретно-событийная | Времена операций, маршруты, буферы, отказы | Средняя | Хорошая по пропускной способности и очередям | Производственные линии, логистика, склады |
| Агентная | Правила поведения агентов, среда | Средняя — высокая | Качественная, чувствительна к правилам | Трудовая мобильность, транспорт, эвакуация |
| Статистическая | Исторические ряды, факторы | Низкая | Зависит от стационарности | Прогноз спроса, нагрузки, сезонности |
| Машинное обучение | Размеченные или объёмные исторические данные | Высокая при обучении, низкая при выводе | Высокая внутри распределения обучения | Диагностика, аномалии, прогноз остаточного ресурса |
| Графовая | Объекты и связи, топология сети | Низкая — средняя | Точна по структуре, не по физике | Зависимости, точки отказа, цепочки поставок |
| Онтологическая / семантическая | Понятия, отношения, правила | Низкая | Не численная, обеспечивает согласованность | Интеграция доменов, единый словарь, вывод по правилам |

Главный компромисс: **точность стоит вычислений и данных**. Полевая модель даст лучший ответ, но не в оперативном контуре. Поэтому в двойнике почти всегда сосуществуют две модели одного явления: детальная для проектных расчётов и редуцированная для оперативного применения.

## 2. Редуцированные и суррогатные модели

Схема получения ROM:

```
[Полная модель CFD/FEM]
        │  серия расчётов по плану эксперимента (100–1000 точек)
        ▼
[Выборка: входы X → отклики Y]
        │  снижение размерности (POD/PCA) или обучение аппроксиматора
        ▼
[ROM / суррогат]  ── расчёт за миллисекунды вместо часов
        │
        ▼
[Проверка на отложенных точках] → метрика ошибки, границы применимости
```

Требования к корректному применению ROM:

- зафиксирована **область применимости** — диапазоны входных параметров, в которых модель валидна;
- измерена ошибка на отложенной выборке и указана в карточке модели;
- на входе действует проверка, что запрос попадает в область применимости, иначе возвращается отказ или предупреждение;
- при изменении объекта или условий эксплуатации ROM переобучается — это регламентная операция, а не разовая.

Экстраполяция за пределы обученной области — самая частая причина уверенно неверных ответов двойника.

## 3. Композиция моделей и co-simulation

Реальный двойник — не одна модель, а связка. Пример для транспортно-производственного узла:

```
┌──────────────┐   план выпуска    ┌──────────────────┐
│ Статистическая│ ────────────────► │ Дискретно-       │
│ модель спроса │                   │ событийная модель│
└──────────────┘                   │ производства     │
                                    └────────┬─────────┘
                     потребность в перевозках │
                                    ┌─────────▼────────┐   загрузка сети
┌──────────────┐  состояние узлов   │ Графовая модель  │ ──────────────►
│ ML-модель     │ ─────────────────►│ логистической    │
│ отказов узлов │                    │ сети             │
└──────────────┘                    └────────┬─────────┘
                                              │ маршруты, узкие места
                                    ┌─────────▼────────┐
                                    │ ГИС-представление│
                                    └──────────────────┘
```

Правила композиции:

| Правило | Смысл |
|---------|-------|
| Явный контракт между моделями | Для каждой связи заданы величины, единицы, частота и допустимый диапазон |
| Согласование шага времени | Модели с разным шагом связываются через интерполяцию или буфер, а не «как получится» |
| Единая система координат и единиц | Расхождение единиц — источник самых дорогих ошибок |
| Отслеживание накопления погрешности | Ошибка первой модели входит во вторую; требуется оценка сквозной погрешности |
| Возможность отключения звена | При недоступности модели используется заглушка с консервативной оценкой |

Co-simulation — совместный запуск моделей разных сред с обменом данными на каждом шаге. Отраслевой стандарт обмена — FMI/FMU, позволяющий упаковать модель в переносимый компонент.

## 4. Версионирование моделей

Модель без версии невоспроизводима, а невоспроизводимый расчёт нельзя защитить перед заказчиком или проверяющим.

Правило: версионируется **тройка** «код модели + параметры/веса + набор данных». Изменение любого элемента даёт новую версию результата.

```yaml
model:
  id: MDL-2026-07-scenario-logistics
  version: 3.2.0
  type: graph + optimization
  created: 2026-07-14
  owner: "аналитик домена «Транспорт»"
input:
  datasets:
    - id: DS-roads-osm
      snapshot: 2026-06-30
    - id: DS-industry-rosstat
      snapshot: 2026-Q1
  parameters_hash: "a41f9c..."
assumptions:
  - "Пропускная способность дороги оценивается по классу, а не по фактическим замерам"
  - "Сезонные ограничения учитываются только для дорог с указанным атрибутом"
limits:
  - "Не применима к внутригородской логистике"
  - "Не учитывает мультимодальные перевалки"
validation:
  method: "сверка с историческими маршрутами за 2025 год"
  metric: "MAPE по времени доставки"
  value: 0.14
output:
  artifacts: ["маршруты", "узкие места", "оценка времени доставки"]
```

Такая карточка модели (model card) обязана сопровождать каждую модель, попадающую в продуктив.

## 5. Представления для разных ролей

Одна и та же расчётная сущность выглядит по-разному для разных пользователей. Ошибка — показывать всем одно и то же.

| Роль | Вопрос пользователя | Представление | Горизонт | Что скрыть |
|------|---------------------|---------------|----------|------------|
| Инженер-технолог | Почему параметр отклоняется? | Тренды, сравнение с моделью, разбор остатка | Часы — сутки | Финансовые агрегаты |
| Оператор | Что делать сейчас? | Мнемосхема, 3–5 показателей, явное действие | Минуты | Детали расчёта модели |
| Диспетчер / ситуационный центр | Где риск и какие ресурсы доступны? | Карта, статусы, маршруты, резервы | Часы | Первичные записи чувствительных слоёв |
| Аналитик | Какой сценарий лучше? | Сравнение вариантов, чувствительность, допущения | Недели — годы | Оперативная телеметрия |
| Руководитель | Каков итог и цена решения? | 5–7 показателей, тренд, отклонение от плана | Месяцы — годы | Технические подробности |
| Разработчик модели | Насколько модель адекватна? | Метрики качества, дрейф, ошибки на валидации | Постоянно | — |

Общее требование ко всем представлениям: рядом с числом должен быть указан источник, время актуальности и, для расчётных величин, — модель и её версия. Число без контекста порождает ложную уверенность.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Выбор самой точной модели вместо подходящей | Кажется, что точность не бывает лишней | Исходить из требуемой точности решения, а не из максимума возможного |
| Применение ROM за пределами обученной области | Модель отвечает на любой вход | Явная проверка области применимости с отказом при выходе за границы |
| Модель без карточки и версии | Разработка идёт быстрее, чем документирование | Модель без карточки не допускается в продуктив |
| Единая витрина для всех ролей | Экономия на проектировании интерфейса | Отдельные представления по ролям и горизонтам решений |
| Игнорирование накопленной погрешности в цепочке | Каждая модель проверялась отдельно | Оценка сквозной погрешности композиции |
| ML вместо физики там, где физика известна | Мода на машинное обучение | Использовать данные для калибровки физической модели, а не подменять её |
| 3D-визуализация как замена модели | Красивая картинка принимается за двойник | Разделять представление и расчётное ядро |

## Пример: «Цифровой двойник России»

В [MVP.md](../../MVP.md) прямо сказано, что для MVP достаточно простых моделей: изменение доступности объекта при отключении одного маршрута, оценка кадрового дефицита при запуске нового производства, сравнение площадок по расстоянию до ресурсов, кадров и транспортных узлов, оценка риска ЧС по историческим и географическим признакам, расчёт базовых показателей нагрузки на инфраструктуру.

Сопоставление сценариев MVP с классами моделей:

| Сценарий MVP | Класс модели | Основные входные данные |
|--------------|--------------|-------------------------|
| Доступность при отключении маршрута | Графовая (связность сети) | Дорожный граф OSM, узлы, объекты |
| Кадровый дефицит при запуске производства | Статистическая и балансовая | Вакансии, занятость, выпуск образовательных организаций |
| Сравнение площадок | Многокритериальная оценка на ГИС-основе | Расстояния, инфраструктура, кадры, ограничения |
| Риск ЧС | Статистическая по историческим и географическим признакам | Ряды Росгидромета, реестры МЧС, рельеф, землепользование |
| Нагрузка на инфраструктуру | Балансовая | Мощности, потребление, численность населения |

Требования проекта к моделям прямо совпадают с материалом темы: каждая модель сопровождается описанием допущений, входных данных и ограничений применимости; модели версионируются вместе с наборами данных, на которых обучены или валидированы; результат сопровождается цепочкой расчёта, доступной пользователю в журнале; спорные сценарии проверяются минимум на двух независимых наборах допущений. Метрика безопасности и качества «доля моделей с карточкой (model card) — 100 %» делает карточку обязательным артефактом.

Представления в проекте также ролевые: [Описание](../../Описание.md) выделяет карту и 3D-модель, аналитические панели, отчёты и API для разрешённых наборов данных, а состав аудитории — от федеральных органов и региональных правительств до операторов инфраструктуры, служб занятости, науки, бизнеса и граждан. Ключевое ограничение представлений — контурное: пользователи получают только тот объём информации, который нужен для их роли и задачи.

## Практическое задание

Спроектируйте модельный слой сквозного проекта.

1. Сформулируйте три вопроса, на которые двойник должен отвечать, и подберите класс модели под каждый.
2. Для каждой модели заполните строку таблицы «входные данные → стоимость расчёта → точность → применимость».
3. Постройте композицию минимум из двух моделей и опишите контракт связи между ними.
4. Для одной модели оформите полную карточку с допущениями, ограничениями, версией и метрикой валидации.
5. Опишите, где применима редуцированная модель и как проверяется область её применимости.
6. Спроектируйте два представления результата для двух разных ролей.

Критерии приёмки:

- [ ] Класс модели выбран из требуемой точности решения, а не по максимуму возможностей
- [ ] Для каждой модели указаны входные данные и порядок стоимости расчёта
- [ ] Контракт между моделями задаёт величины, единицы, частоту и диапазоны
- [ ] Карточка модели содержит допущения, границы применимости и числовую метрику валидации
- [ ] Указана версия набора данных, на котором модель валидирована
- [ ] Описана реакция системы на запрос вне области применимости
- [ ] Два представления различаются составом показателей и горизонтом, а не только оформлением

## Проверочные вопросы

1. В каких случаях полевая модель (FEM/CFD) неприменима в оперативном контуре и чем её заменяют?
2. Как строится ROM и какие проверки обязательны перед его применением?
3. Почему версионируется тройка «код + параметры + данные», а не только код?
4. Чем графовая модель полезна для анализа критической инфраструктуры и чего она не даёт?
5. Как оценить сквозную погрешность цепочки из трёх моделей?
6. Почему 3D-визуализация не является цифровым двойником?
7. Какие поля обязательны в карточке модели, чтобы расчёт был воспроизводим?
