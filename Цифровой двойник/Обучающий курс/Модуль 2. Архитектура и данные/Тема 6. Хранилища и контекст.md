# Модуль 2. Тема 6. Хранилища и контекст

> Модуль 2 «Архитектура и данные» · Тема 6 из 6

## Учебные цели

После изучения темы студент сможет:

- подбирать тип хранилища под характер данных и профиль обращения к ним;
- проектировать медальонную архитектуру слоёв обработки от сырых данных до витрин;
- строить контекстный слой: единую идентификацию объектов, иерархии активов и связи;
- организовывать каталог данных, метаданные и происхождение (lineage);
- задавать политику ретеншна, воспроизводимости расчётов и разграничения доступа на уровне данных.

## Ключевые понятия

| Термин | Определение |
|--------|-------------|
| Time series БД | Хранилище, оптимизированное под запись и чтение временных рядов с метками времени |
| Озеро данных | Объектное хранилище сырых файлов произвольных форматов с дешёвым масштабированием |
| Медальонная архитектура | Разделение данных на слои raw/bronze, cleansed/silver, curated/gold с ростом качества и готовности |
| НСИ / мастер-данные | Эталонные справочники объектов, обеспечивающие единое понимание сущностей во всех системах |
| Единый идентификатор | Стабильный ключ объекта, не зависящий от системы-источника и места расположения |
| Каталог данных | Реестр наборов данных с описанием, схемой, владельцем, качеством и правами доступа |
| Lineage | Прослеживаемая цепочка происхождения данных от источника до конечного показателя |
| Ретеншн | Политика сроков хранения данных по слоям и классам |
| Снимок набора данных | Зафиксированная версия данных на момент времени, обеспечивающая воспроизводимость расчёта |
| Разграничение на уровне данных | Ограничение доступа к строкам, столбцам и точности значений, а не только к экрану |

## 1. Типы хранилищ

| Тип данных | Хранилище | Почему именно оно |
|------------|-----------|-------------------|
| Технологические измерения, метрики | Time series БД (историан) | Сжатие рядов, быстрые агрегаты по времени, downsampling |
| Реестры объектов, справочники, транзакции | Реляционная СУБД | Целостность, связи, транзакции, зрелый SQL |
| Геометрия, слои, границы, маршруты | Пространственная БД (PostGIS) | Пространственные индексы и операции, проекции координат |
| Сырые файлы, выгрузки, снимки, отчёты | Объектное хранилище | Дешёвое хранение больших объёмов, неизменяемость версий |
| Связи, зависимости, топология сетей | Графовая БД | Обход связей и поиск путей без каскада соединений |
| Слабоструктурированные документы, паспорта, JSON | Документная БД | Гибкая схема, вложенные структуры |
| Логи и события платформы | Журнальное хранилище с индексом | Полнотекстовый поиск, ретеншн по времени |
| Обученные модели, веса, артефакты | Реестр моделей | Версии, метрики, привязка к данным обучения |
| Признаки для ML | Хранилище признаков (feature store) | Одинаковые признаки при обучении и при выводе |

Практическое правило: не пытайтесь свести всё в одну СУБД, но и не заводите новое хранилище без ответа на вопрос, какой профиль запросов оно обслуживает. Для MVP разумный минимум — реляционная база с пространственным расширением плюс объектное хранилище; всё остальное добавляется по мере доказанной необходимости.

## 2. Медальонная архитектура

```
┌───────────────────────────────────────────────────────────────┐
│  RAW / BRONZE — как пришло от источника                       │
│  Неизменяемые файлы и записи, исходные форматы, метка загрузки │
│  Никаких правок. Хранит правду источника, включая ошибки       │
└───────────────────────┬───────────────────────────────────────┘
                        │ парсинг, типизация, проверки качества,
                        │ дедупликация, приведение к UTC
┌───────────────────────▼───────────────────────────────────────┐
│  CLEANSED / SILVER — очищено и приведено к единой модели       │
│  Единые идентификаторы, классификаторы, единицы измерения      │
│  Записи, не прошедшие проверку, — в карантин с причиной        │
└───────────────────────┬───────────────────────────────────────┘
                        │ агрегация, расчёт показателей,
                        │ применение моделей, денормализация
┌───────────────────────▼───────────────────────────────────────┐
│  CURATED / GOLD — витрины для потребления                      │
│  Показатели, слои карты, наборы для API, срезы для контуров    │
└───────────────────────────────────────────────────────────────┘
```

| Слой | Кто пишет | Кто читает | Изменяемость | Типовой ретеншн |
|------|-----------|------------|--------------|-----------------|
| Raw | Только пайплайны загрузки | Инженеры данных, аудит | Неизменяем | 24–36 месяцев |
| Cleansed | Пайплайны обработки | Модели, аналитики | Перестраиваемый из raw | 36–60 месяцев |
| Curated | Пайплайны витрин | API, интерфейс, отчёты | Полностью перестраиваемый | По потребности сценариев |

Главное свойство схемы: **любой вышележащий слой воспроизводим из нижележащего**. Если витрину нельзя пересобрать из сырых данных, значит, где-то в цепочке потеряна информация или применена недокументированная ручная правка.

## 3. Контекст: идентификация, иерархии, связи

Измерение без контекста бесполезно. Значение «6,42» приобретает смысл только когда известно: это давление на выходе насоса П-101, в барах, на насосной станции №3, в 08:41 UTC, при рабочем режиме агрегата.

Контекст складывается из четырёх элементов:

**Единая идентификация.** У каждого объекта — стабильный внутренний идентификатор платформы и таблица соответствий внешним ключам систем-источников.

```sql
CREATE TABLE mdm.object_registry (
    object_uid    UUID PRIMARY KEY,
    object_type   TEXT NOT NULL,
    name          TEXT NOT NULL,
    valid_from    TIMESTAMPTZ NOT NULL,
    valid_to      TIMESTAMPTZ,
    parent_uid    UUID REFERENCES mdm.object_registry(object_uid)
);

CREATE TABLE mdm.object_xref (
    object_uid    UUID NOT NULL REFERENCES mdm.object_registry(object_uid),
    source_system TEXT NOT NULL,     -- 'ERP', 'MES', 'OSM', 'ЕМИСС'
    source_key    TEXT NOT NULL,
    confidence    NUMERIC(3,2) NOT NULL DEFAULT 1.00,
    PRIMARY KEY (source_system, source_key)
);
```

**Иерархии активов.** Территориальная (страна → округ → регион → муниципалитет), организационная (холдинг → предприятие → цех → линия → агрегат), функциональная (система → подсистема → узел). Один объект может входить в несколько иерархий одновременно, поэтому иерархия хранится отдельно от объекта.

**Связи между объектами.** Зависимость, питание, поставка, замещение, близость. Именно связи позволяют отвечать на вопросы вида «что перестанет работать при отказе этого узла» — задача, которую невозможно решить на плоских таблицах.

**Семантический слой.** Единый словарь показателей: что такое «загрузка мощности», как она считается, в каких единицах. Без него один и тот же термин в двух отчётах означает разное, и расхождение обнаруживается на совещании, а не в системе.

## 4. Каталог данных, метаданные и происхождение

Каталог отвечает на вопросы пользователя до обращения к данным: что это, откуда, насколько свежо, кому принадлежит, можно ли использовать.

| Категория метаданных | Содержание | Пример |
|----------------------|------------|--------|
| Технические | Схема, типы, объём, формат, партиционирование | 42 столбца, 18 млн строк, партиции по месяцам |
| Бизнес-метаданные | Смысл показателей, единицы, методика расчёта | «Дефицит профессии = вакансии − доступные соискатели» |
| Операционные | Время последней загрузки, статус, длительность, ошибки | Загружено 2026-07-19 03:04, успешно, 4 мин |
| Качество | Значения метрик по пяти измерениям, доля карантина | Полнота 0,993; дублей 0,0004 |
| Управленческие | Владелец, ответственный, срок пересмотра | Владелец — Минтруд, пересмотр — ежегодно |
| Правовые | Лицензия, правовое основание, контур доступа | Открытые данные, открытый контур |

Lineage фиксирует путь показателя:

```
[ЕМИСС: показатель занятости]        [«Работа России»: вакансии]
             │                                   │
             ▼                                   ▼
   raw.emiss_employment@2026-Q1     raw.trudvsem_vacancies@2026-07-18
             │                                   │
             └──────────► cleansed.labor_market ◄┘
                                │
                                ▼
                    curated.regional_skill_gap
                                │
                                ▼
                    API /v1/regions/{id}/skill-gap
```

Ценность lineage проявляется при инциденте: если в источнике обнаружена ошибка, за минуты определяется список затронутых витрин, API и отчётов, а также пользователей, которым нужно сообщить о пересчёте.

## 5. История, ретеншн и воспроизводимость

Двойник обязан отвечать не только на вопрос «как сейчас», но и «как было» и «что мы знали на тот момент». Это два разных вопроса, и они требуют двух разных меток времени.

| Тип времени | Что означает | Зачем нужно |
|-------------|--------------|-------------|
| Время события (valid time) | Когда состояние было верно в реальности | Анализ фактической истории объекта |
| Время записи (transaction time) | Когда система узнала об этом | Воспроизведение расчёта, сделанного в прошлом |

Хранение обеих меток называется битемпоральным и позволяет ответить: «какой прогноз выдала бы система 1 марта на тех данных, что были доступны 1 марта». Без этого невозможно ни разобрать спорное решение, ни честно оценить качество прошлых прогнозов.

| Механизм | Назначение | Стоимость |
|----------|------------|-----------|
| Снимок набора данных | Фиксация версии входа для воспроизводимости расчёта | Дублирование объёма, снижается дедупликацией |
| Медленно меняющиеся измерения (SCD2) | История изменений справочников с интервалами действия | Рост таблиц справочников |
| Понижение детальности старых рядов | Секундные данные за 30 суток, минутные за год, часовые за 5 лет | Потеря детализации, экономия в разы |
| Холодное хранение | Перенос редко используемых данных в дешёвый класс | Задержка при доступе |
| Полное удаление по сроку | Исполнение правовых требований и снижение риска | Безвозвратно, требует регламента |

Политика ретеншна задаётся по классам данных, а не единым сроком для всей платформы: сырые файлы источников, технологические ряды, персональные и чувствительные данные, журналы аудита и артефакты моделей живут по разным правилам.

## 6. Разграничение доступа на уровне данных

Ограничение доступа только в интерфейсе не является защитой: API и прямые запросы к базе обойдут его. Разграничение должно действовать на уровне самих данных.

| Механизм | Что ограничивает | Пример |
|----------|------------------|--------|
| Построчная безопасность (RLS) | Набор доступных записей | Регион видит объекты только своей территории |
| Ограничение столбцов | Отдельные атрибуты | Точные координаты скрыты, доступен только муниципалитет |
| Обобщение и агрегирование | Точность значения | Координата округляется до сетки, значения — до диапазона |
| Маскирование | Идентификаторы и персональные данные | Ключ заменяется псевдонимом |
| Отдельные витрины по контурам | Физическое разделение наборов | Открытый контур получает собственную витрину агрегатов |
| Аудит обращений | Фиксация факта доступа | Журнал запросов с автором, временем и составом выборки |

Наиболее надёжный подход для чувствительных данных — не фильтрация общей витрины, а **построение отдельной витрины для внешнего контура**, куда попадают только агрегаты, прошедшие проверку на риск реидентификации.

## Типичные ошибки

| Ошибка | Почему возникает | Как избежать |
|--------|------------------|--------------|
| Правка данных в сыром слое | Хочется быстро исправить ошибку источника | Raw неизменяем; исправления — правилами в слое очистки |
| Одно хранилище под все задачи | Стремление к простоте эксплуатации | Выбор хранилища по профилю запросов, но без избыточного зоопарка |
| Отсутствие единых идентификаторов | Каждая система приносит свой ключ | Реестр объектов и таблица соответствий с первого источника |
| Витрина, не пересобираемая из raw | Ручные правки и недокументированные шаги | Требование полной воспроизводимости витрин |
| Каталог данных ведётся в таблицах вручную | Кажется избыточным на старте | Метаданные наполняются пайплайнами автоматически |
| Единый срок хранения для всего | Проще согласовать | Политика ретеншна по классам данных |
| Доступ ограничен только интерфейсом | Защита добавлена на позднем этапе | RLS, ограничение столбцов, отдельные витрины контуров |
| Расчёт без фиксации версии данных | Никто не спрашивал о воспроизводимости | Снимки наборов и битемпоральное хранение |

## Пример: «Цифровой двойник России»

Технологический контур MVP из [MVP.md](../../MVP.md) прямо соответствует материалу темы: PostgreSQL/PostGIS как пространственная база данных, объектное хранилище для архивов, снимков, отчётов и выгрузок, каталог метаданных как отдельный компонент архитектуры, Apache Airflow для расписания загрузок.

Медальонная логика видна в цепочке из [Источников CSV и API](../../Источники%20CSV%20и%20API.md): загрузка файла → нормализация и паспорт качества → PostGIS и объектное хранилище → каталог метаданных с полем `source_version`, равным дате выгрузки. Последнее и есть механизм снимков, обеспечивающий воспроизводимость: расчёт всегда можно повторить на той версии данных, на которой он выполнялся.

Требования MVP к контексту сформулированы как функциональные требования к сбору и нормализации: приведение адресов, координат, классификаторов и временных периодов к единому формату; хранение источника, даты обновления, лицензии, качества и ответственного владельца данных; базовые проверки на дубликаты, пустые координаты, устаревшие значения и конфликтующие записи. Единая идентификация решается через классификаторы, перечисленные в [Источниках CSV и API](../../Источники%20CSV%20и%20API.md): ОКТМО, ОКВЭД2, ОКПД2, ОКЗ, ОКСО и государственный адресный реестр ГАР.

Разграничение доступа на уровне данных в проекте реализовано как система контуров — открытый, ведомственный, инфраструктурный, закрытый, исследовательский. Правило передачи между контурами, описанное в [Примерах обработки информации для контуров](../../Примеры%20обработки%20информации%20для%20контуров.md), полностью соответствует подходу «отдельная витрина для внешнего контура»: наружу выходят выводы, ограничения и обезличенные агрегаты, а не первичные записи. Меры против реидентификации — k-анонимность, подавление редких категорий, регулярная проверка — являются частью правил построения витрины открытого контура, а не настройкой интерфейса.

Метрики MVP закрепляют эти требования численно: доля слоёв с паспортом качества — 100 %, доля операций передачи между контурами с записью в журнал — 100 %, доля наборов с подтверждённым обезличиванием для открытого контура — 100 %, регулярные проверки риска реидентификации — не реже раза в квартал.

## Практическое задание

Спроектируйте слой хранения и контекста для сквозного проекта.

1. Для каждого класса данных из вашего каталога источников выберите тип хранилища и обоснуйте выбор профилем запросов.
2. Опишите три слоя медальонной архитектуры: что попадает в каждый, кто пишет, кто читает, как перестраивается.
3. Спроектируйте реестр объектов с единым идентификатором и таблицей соответствий внешним ключам минимум трёх систем.
4. Постройте не менее двух иерархий объектов и опишите три типа связей между объектами.
5. Составьте карточку каталога для одного набора данных по шести категориям метаданных.
6. Нарисуйте lineage одного показателя от источников до потребителя.
7. Задайте политику ретеншна по классам данных и опишите механизм разграничения доступа для чувствительного слоя.

Критерии приёмки:

- [ ] Выбор каждого хранилища обоснован профилем запросов, а не привычкой
- [ ] Сырой слой объявлен неизменяемым, описан порядок исправления ошибок источника
- [ ] Показано, что любая витрина пересобирается из сырого слоя
- [ ] Реестр объектов содержит стабильный внутренний идентификатор и соответствия трём системам
- [ ] Иерархии хранятся отдельно от объектов и допускают вхождение объекта в несколько иерархий
- [ ] Карточка каталога заполнена по всем шести категориям метаданных
- [ ] Схема lineage доводит показатель от источников до конкретного потребителя
- [ ] Ретеншн задан по классам данных, разграничение доступа действует на уровне данных, а не интерфейса

## Проверочные вопросы

1. Почему сырой слой должен оставаться неизменяемым и как тогда исправлять ошибки источника?
2. Что означает требование воспроизводимости витрины из сырого слоя и как его проверить?
3. Зачем нужен внутренний идентификатор объекта, если у источников уже есть свои ключи?
4. Чем время события отличается от времени записи и какой вопрос без второй метки неразрешим?
